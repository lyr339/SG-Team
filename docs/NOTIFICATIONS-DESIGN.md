# 拾光消息通知系统设计规划

本规划面向拾光的用户和后续实现者，依据 v0.5.15 对应源码梳理。目标不是增加更多弹条，而是让用户知道发生了什么、哪些事需要自己处理、处理入口在哪里，并在多会话并行时减少打断。以下系统设计均为拟实施方案，不代表已经实现。

设计提出时仅移除更新提醒左侧的彩色粗边；下文的“当前状态”是当时基线。实际分批实现、证据与未完成范围以 `NOTIFICATIONS-IMPLEMENTATION.md` 为准，不将本规划或单批验收当作完整完成。

规划复核将会话上线、离线、恢复和自动化完整结果列为首期必做，不再用「连接异常」和「最终结果」两个总称代替。实现范围按下文业务事件清单和场景验收，不以做出通知浮层作为完成标准。

跨页面体验的原则是完整覆盖、克制送达。记录业务事实不等于必须弹出提醒，事件重要也不一定需要全局横条；用户就在操作处时以就地结果为主，离开后才适度升级。后文的低打扰默认策略优先于「所有核心事件都弹出」的理解。

## 当前状态和边界

- `UpdateReminder.tsx`：独立的右下角更新提醒，15 秒自动收起；「稍后」调用主进程的 24 小时延后规则，设置入口另有更新角标。
- `settings/SettingsNotice.tsx`：设置页独立反馈，已有中性表面、语义图标、可展开详情与关闭按钮，可复用其视觉原则。
- `run/PoolPage.tsx`：运行页以局部 error / notice 状态显示结果，与更新提醒不共用历史、队列或去重。
- 会话、问卷、交接、导入、组管理等组件也有就地反馈。它们并不都应该变成全局通知。
- `desktop-api.ts` 已有更新、批量发起、自动化、会话、任务和协作快照订阅；没有统一通知记录或人类通知已读接口。源码未发现 Electron 原生通知发送实现。
- Agent 团队消息已有投递、读取和回复回执。这是业务通信，不是人类通知中心的已读状态，必须保持独立。

复核后确认的关键事实：

- 会话最终状态由 `channel-message-relay.ts`、`verify-agent-runtime.ts` 和 `desktop-session-service.ts` 分层投影。`online=false` 不一定是 Cursor 已停止：`runtimeEvidence` 明确区分 `suspected` 与 `stopped`。领域层待命活性窗口为 120 秒，processing / need_reply_sync 为 5 分钟，CDP 新鲜活动还能维持在线；通知不得另写一套心跳超时判定。
- 终止相位包括 cursor_stopped、tool_aborted 和 retired；其中 retired 可以来自运行作用域退役，不能把它一律写成意外断线。死亡证据还可能被更新的真实生命证据推翻，通知必须服从最终校验投影。
- `agent-session-launcher.ts` 在全部创建请求已提交时可触发自动化；这早于全部 Agent 进入待命。创建提交成功、会话上线、全部会话可用是不同事件。
- `AccountAutomationRun` 除主 phase 外，还有并行的 handover 子状态。`finishDeletedAccount` 会在清场或本地记录移除异常时仍给出 done；看门狗超时也不等于支线最终失败。直接按 phase=done 弹绿色「全部成功」是错误设计。
- 自动化运行状态当前在服务内存中，`runSeq` 也是私有的；不能承诺应用崩溃后恢复每个中间步骤。通知规划需要最小可观察身份和结构化结果，不从自然语言 message 里猜业务完成情况。
- `SendMessageAccepted` 只返回 commandId，交接结果也可能只是 held 或已排队。接口返回不等于 Agent 已读取，更不等于完成回复。
- `SettingsPage.tsx` 的八个分组用 hidden 隐藏，而不是切换时全部卸载；公共 `SettingsNotice` 在分组内容之前，现有消息结构只有 tone / title / detail，没有原页面归属。不能因为回调正在执行或组件仍挂载，就判断用户正在看它；跨子页共享提示需要显式来源。
- 右栏的文件动作已经在 `use-workspace-file-actions.ts` 中复用局部 flash，统计页也明确冻结隐藏状态下的视图。新系统要尊重已有局部反馈和性能边界，不把这些全部改成全局事件。

不改变批量发起、账号、自动化、MCP 或消息投递的控制逻辑，不为通知再加预检、网络请求或额外轮询。通知失败不能导致业务失败；通知动作不能绕开现有确认和权限检查。

## 用户端采用四层反馈

| 层级 | 适合的内容 | 呈现规则 |
| --- | --- | --- |
| 就地反馈 | 输入校验、复制成功、正在提交、当前页操作进度 | 在原按钮、表单或卡片附近出现，不进入通知历史 |
| 短暂提醒 | 用户离开操作处后的重要结果、新的待处理事项或影响运行的异常 | 统一右下角入口，默认同时一张；普通完成约 5 秒，带操作约 10 秒；不给每个正常状态变化弹条 |
| 通知中心 | 值得回看的结果、待处理事项、更新和持续异常 | 顶栏入口，持久化摘要，按来源定位，不替代会话或任务原始记录 |
| 系统通知 | 用户离开拾光后出现的会话上下线、流程完成、待处理事项和重要失败 | 后台且用户允许该类别时发送；默认静音、隐藏敏感正文；拒绝或不支持时回退中心 |

「待处理」由业务事实决定，即使短暂提醒自动收起，事项仍在通知中心的待处理区。关闭弹条、标为已读、稍后提醒、业务已解决、归档是不同动作，不合并成一个 dismiss。

### 通知中心布局

顶栏在设置入口附近提供细线铃铛和克制的未读数字，不加常亮装饰点，也不挤占工作区名称。桌面端点击展开右侧临时浮层，不取代已有会话右栏，不改变左右栏宽度或开关。窄窗改为宽面板，保留可靠的关闭和返回。

面板采用「全部 / 待处理 / 未读」三个入口；待处理置顶，其他按最近有效变化排序。每条展示来源、标题、必要摘要、时间以及一个明确主操作，例如「打开会话」「查看失败项」「查看更新」。详情按需展开，技术诊断默认折叠。

可筛选当前工作区或所有工作区；全局更新和设备级异常始终可见。切换工作区不删除历史、不把原工作区事件改挂到新工作区。其他工作区的消息明确显示所属位置；跳转会导致工作区切换时先确认，不悄悄切换 Cursor。

主数字表示未读主通知数，不累计同一异常的重复次数；属于同一操作的步骤和成员明细不重复计数。没有共同父操作的独立事件，即使 Toast 视觉聚合，仍分别计入中心未读；不能用视觉合并悄悄改变数量。待处理条数在面板内单独说明。「全部已读」只影响当前明确过滤范围，不隐藏待处理事项。展开列表不会立刻清空未读；打开某条详情，或原业务页面中目标事项实际可见且窗口有焦点，才确认该条已读。仅选中会话或进入运行页不代表看到所有新通知。

普通活动记录与需要用户知晓／处理的通知分开：日常上线、正常停止等必要生命周期记录不参与未读徽标，不虚假写入已读时间。中心「全部」中可折叠查看日常动态；「未读」只展示需要阅读确认的通知，「待处理」始终由真实业务决定。默认入口优先显示待处理和有意义结果，不铺满成功流水账。普通参数编辑、主题切换、筛选和复制本就不写通知历史，不为实现安静模式另造一套活动日志。

### 提醒卡片视觉

- 使用现有主题表面和字号变量，四边同色 1px 细边框，无彩色左边、满底红绿、渐变胶囊或装饰脉冲。
- 标题约 14px、摘要约 13px、来源与时间约 12px，均使用现有系统字体；留白与文字量匹配。
- 推荐宽度 360–420px；长文自然换行，长路径可折行，详情不塞进窄弹条。窄窗不超出安全边界。
- 状态色只落在小型线性图标和状态文字；拾光主题色只用于主操作和明确选择态，不能用橙色冒充错误或警告。
- 一条最多一个主操作、一个轻量次操作和关闭；不把整张卡做成隐形按钮，不让关闭误触发跳转。
- 入场和收起约 160–200ms，只用 opacity / transform；焦点或鼠标在卡内、窗口失焦时暂停自动消失，恢复后继续剩余时长，不重置为完整时长。尊重减少动画设置。
- 暂停的是展示停留计时，不延长事件的候选有效期；回到前台时，过期的普通成功提示不补弹，历史仍可查看。
- 显示消息不抢焦点；主动打开中心才管理焦点。Esc 只关闭最上层，关闭后回到触发按钮；弹条不是模态框。

## 各页面的反馈与通知映射

以下覆盖现有主模块、八个设置子页、右栏和常用弹层。不是让每页多放一条提示，而是将提示固定在最相关的位置，并为离页后才发生的重要结果提供可靠去处。

| 页面或区域 | 默认就地反馈 | 何时进入通知中心或短暂提醒 | 不应该打扰用户的内容 |
| --- | --- | --- | --- |
| 顶栏工作区与连接 | 工作区名称、连接状态、展开后的诊断 | 明确影响正在运行的批次、需要用户配置的持续异常；单一故障汇总 | 每次检测、普通工作区识别和短暂重连，不弹「检测成功」 |
| 外观设置 | 预览变化、当前选中项；保存失败留在相关控件旁 | 只有持续无法保存且用户已离开时提示一次；不把预览变更当作已落盘 | 主题、背景、透明度拖动和面板开合 |
| 运行页和批次配置 | 创建进度、模型保存、校验、正常操作结果 | 批次终态、混合失败、离页后的等待结果、影响整组的故障 | 一次模型修改一条 toast；逐席位重复成功；当前页已见的同义结果 |
| 组管理与建组／加人弹层 | 字段错误、提交状态、成员变更、关闭或成功收口 | 用户离开后仍有副作用的异步结果、他处引发且影响当前组的变更、需要人工处理的问题 | 新名称、权限选项、成功勾选成员和普通保存 |
| 会话侧栏与主体 | 在线状态、发送状态、排队、流式结果、原问卷与审批 | 确认意外离线、用户未看到的有意义回复、人工决策；生命周期事实保留但低优先级动态不刷徽标 | 每个 token、每次待命／忙碌切换、用户正在看的回复和每次普通上线 |
| 右栏审查 | 文件操作的局部结果、冲突、回滚确认；保持路径和作用域 | 影响真实变更结果的失败；离页后结束的重要操作可定位到原审查 | 复制路径、打开文件、展开 diff、每次自动刷新和文件计数变化 |
| 右栏计划／活动／产物 | 状态和来源直接显示；复制、打开、定位失败用现有局部 flash | 真正待验收、最终失败、重要保存失败或来源持续不可用 | 每项 todo 切换、每次工具调用、活动流水、普通文件出现 |
| 协同面板与协作图 | 目标、成员、消息和任务变化在原内容呈现 | 明确发给用户的事项、身份迁移的部分结果、当前用户能处理的失败 | 每条 Agent 内部消息、动态连线、鼠标聚焦或图布局变化 |
| 设置中的统计 | 刷新时间、数据质量、费用估算说明；无数据时正确空态 | 仅持续数据异常且需要修复、并且与原界面不同处发生的重要结果 | 用量增长、切换日期／成本／Token、排序翻页；不能发「账单增加」暗示官方扣费 |
| 设置中的账号 | 当前行的选择、登录、导入、删除确认和切换结果；错误定位到对应账号 | 需要重启的切换结果、失败恢复或恢复不明、离页后结束的重要账号操作 | 当前行操作结束却在别的设置子页顶上报成功；普通选择和绑定保存 |
| 设置中的导入来源 | 浏览器、端口、窗口绑定；格式校验与登录错误贴近输入或窗口行 | 离页后的导入／登录结果、持续找不到执行窗口且阻止正在运行的操作 | 列表刷新、自动探测、打开登录页面本身；保存成功不逐项刷屏 |
| 设置中的自动化 | 设置保存、倒计时、当前步骤和原有取消入口 | 全流程终态、部分完成、失败、支线结果改变；用户没在看时一条明确提醒 | 总开关、延时编辑、目标选项、每个中间阶段和倒计时 tick |
| 设置中的处理服务 | 选定服务的卡密校验、余额、手动进度和结果 | 独立长操作结束、凭据或现有余额结果阻止执行、来源确认的不确定结果 | 切服务、刷新余额成功、周期查询错误；不为通知新增余额轮询 |
| 设置中的 Cursor 维护 | 版本检测、补丁状态、策略设置和修复结果 | 兼容性变化影响当前工作、修复或重启失败；用户离页后的重要结果 | 隐藏页面挂载时的检测、每次版本读取、普通策略保存；不把不支持版本夸大为整套软件不可用 |
| 设置中的存储清理 | 扫描、选中量、阻止原因、确认、执行进度和真实清理结果 | 离页后的清理完成、部分失败、原数据安全受影响的错误 | 首次扫描、勾选、阈值变化、取消确认；预估空间不能写成实际释放 |
| 设置中的软件更新 | 检查、下载进度、已就绪、门禁确认和安装结果 | 新版本轻提醒、离页后的下载完成或失败、升级／回滚结果 | 已是最新版、自动检查的短暂网络失败、每个下载百分比；不催促下载安装 |
| 交接、模型配置及其他确认弹层 | 草稿、字段验证、保存状态、成功结果与风险确认 | 部分交接完成、重要异步结果；必要时明确回到原弹层或原业务页 | 取消、Esc、文件选择器取消、菜单选择；关闭弹层不等于取消已提交操作 |

### 跨页面归属与升级规则

结果携带 originPage / originSection、operationId、原实体身份和作用域。scope 和操作归属用于判断在哪里呈现，不把当前路由当作原来源。

1. 用户仍在相关页面、目标控件或结果实际可见：按钮／行／表单反馈承担结果，不重复出现全局 toast。值得追溯的重要结果可存中心，但被可靠确认可见后不制造未读提醒。
2. 用户切到另一页，长操作才返回：不把原错误条挂到新页。重要结果进入中心，必要时一张摘要，例如「账号导入完成 · 查看账号」；普通短操作不因为离页就自动升级。
3. 同一个设置页面仍要区分八个子页、选定的服务商和账号。隐藏组件、被折叠的右栏、后台窗口及图中的非可见详情都不算用户正在看。
4. 旧请求晚到，只能更新原操作结果或历史；不能清空当前新草稿、改写新服务商反馈，或将错误移到同 CH 的新会话上。
5. 异常需要用户处理，但用户正在正确位置：保留清晰、可操作的就地错误或原业务闸门。通知中心可同步待处理事实，不为了强调错误再弹同义全局警告。
6. 当前有模态确认或输入：普通全局结果等当前交互结束再呈现，不能挡住确认按钮或让 Tab 跳走。业务原有硬闸门不等通知排队，重要事项可以立即进入中心但不抢焦点。

这一规则同时解决页级公共提示串页、隐藏子页误报、离页结果丢失和多层同时提醒，不需要每个页面重新实现队列或查询。

### 低打扰的默认决策顺序

先判断有无新的、可信的结果；普通渲染、刷新和中间进度直接排除。再判断影响及原操作位置，最后选择送达方式：

- 即时轻操作：只就地反馈，不写历史，不增未读。
- 正常状态变化：原页面显示；必要生命周期事实安静记录，不全局弹出。
- 重要操作结果：用户还在看时就地显示；已经离开时最多一张摘要，中心可回看。
- 需要处理或影响运行：中心保留事项；用户不在处理位置时给一次清晰提醒。
- 后台系统通知：仅以上有意义事项且该类别已启用，系统送达与应用 toast 互斥。

不靠「操作超过两秒就通知」之类时长猜测，也不以红色错误为理由突破用户偏好。用户是否需要这个结果，比事件数量或成功失败标签更重要。

页内结果也要克制：优先一处按钮／行级反馈，确实涉及整页才用一条可关闭的中性状态行，不在每个设置子页堆常驻横幅。标题先说明结果，摘要最多两行，动作使用「查看账号」「查看失败项」等具体词；技术栈、重复进度和原始日志放展开详情。

## 全部业务来源和默认通知策略

| 来源 | 触发条件 | 默认策略 |
| --- | --- | --- |
| 软件更新 | 新版本可用、下载完成、安装结果或明确失败 | 同一版本更新同一记录；沿用现有跳过和延后规则；自动检查的短暂网络失败不弹 |
| 批量发起 | plan 的最终成功、部分失败或失败 | 一次批次一条结果，列出成功和失败数量；逐席位进度留在原页 |
| 会话生命周期 | 首次上线、疑似失联、确认离线、恢复、新代次接入和正常结束 | 每个会话保留事实；常规上下线就地显示并进日常动态，确认的意外离线或用户等待的接入结果才升级；多成员变化聚合 |
| 会话回复 | 已确认的新回复或本轮结果 | 不是 waiting、idle、离线即完成；当前正在看的会话不重复弹，其余默认进中心 |
| 问卷和审批 | 当前会话出现真实未处理的用户决策 | 待处理通知，定位原问卷或审批；普通 Agent 待命不通知 |
| 消息投递与交接 | 已入队、已投递、回复同步异常、上下文交接及成员身份迁移结果 | 不把排队或转录路径生成叫作交接完成；离线积压和部分失败需要可定位的提醒 |
| 组任务 | 明确指向用户的待验收、失败或阻塞 | 任务原始状态驱动解决与失效；Agent 之间普通交流不逐条打扰用户 |
| 协作消息 | 明确发给用户的消息、需要人工处理的协作问题 | 显示摘要并打开原记录；人类已读不写 Agent 回执，也不发送自动回复 |
| 自动化主流程 | 开始、倒计时、执行、仅处理结束、完整完成、带警告完成、失败、取消和中断待核对 | 同轮更新一张流程通知；关键终态明确提醒；倒计时和后台进度不逐帧新增 |
| 自动化并行支线 | 换号准备、执行、待回执、成功、失败；清场成功、失败或结果未知 | 子状态归入父流程详情；主流程完成不掩盖未结束或失败的支线，晚到结果可更新原通知 |
| 独立账号操作 | 导入、登录、切换、会员识别、绑定窗口和独立处理的真实结果 | 使用账号和操作身份关联；切换成功、附带警告、失败恢复原账号和恢复失败分别说明 |
| Cursor 与浏览器连接 | 持续、确认的连接异常或自动恢复失败 | 短断过滤，同一故障更新同一记录；恢复后收口；优先使用已有健康证据 |
| 工作区与本机维护 | 工作区检测和切换、兼容性检查、修复补丁、存储清理结果 | 无修改的探测留在原界面；影响运行的失败进入中心；来源切换不制造会话掉线风暴 |
| 上下文占用 | 可靠数据跨越设定阈值，例如 80% / 95% | 每个会话代次、阈值各一次；用滞回和去重防抖；未知或陈旧值不通知 |
| 普通保存与复制 | 当前界面的即时结果 | 就地反馈，避免通知中心被琐事填满 |

上述阈值和时长为默认建议，可在真实数据验收后微调；不在本次修改已有业务阈值。自动化通知仅陈述该轮实际发生的步骤，不从当前设置推测执行结果。

一批八个会话同时产生新回复，可聚合为「8 个会话有新回复」，可展开具体来源；与审批、问卷有关的事项不能被聚合成无法定位的一条。异常优先于成功，但不替换用户正在阅读或操作的卡片。

普通会话回复保留各自记录，仅提醒呈现做聚合，不再把聚合摘要作为第二条未读记录。批量发起的最终结果以 plan 为一个记录，不同时再生成每个席位的相同成功通知。

已知批量发起、预期重启和自动化的成员事件带父操作归属，记录进该主通知的明细，而不是同时增加一条父成功和八条同义子成功。独立发生的异常不受这个归属静音。批量创建的上线明细更新当前创建通知，最终结果替代进度摘要；通知保留每个成员的首次上线事实和定位入口。

## 会话上线离线和恢复的完整规则

### 会话身份和观测状态先于通知

会话身份取当前真实绑定的 workspaceId / runId / slotId / sessionId / generation / composerId 可用组合。CH 仅用来显示。成员角色调整不必重建会话，新代次或不同 Composer 则不能继承原会话的在线事件或未处理通知。

未知绑定不能强挂到当前页面的工作区或当前账号。未绑定通道可显示已知通信事实，明确归属未知；在身份未校准前，不生成指向某个旧席位的操作。waiting / running / idle 的普通切换不产生新的上下线通知，也不等于完成了一项任务。

通知适配器还要知道当前是否在可靠观测：启动同步、正常观测、来源切换、主机休眠、来源断开。这个门禁只限制通知推断，不更改会话本身的状态机。

启动的第一帧可能为空，业务源水合后才出现存量会话；不能用「空数组 → 有数据」直接判首次上线。各源达到已有就绪信号后建立基线；水合期间只有带明确新操作身份／新生命事件的接入可作为新事件，其余保守作存量恢复。来源没有就绪信号时明确列为接入缺口，不能随便等一个固定秒数后宣布同步完成。

| 事件 | 必须有的事实 | 对用户的表达和处理 |
| --- | --- | --- |
| 首次上线 | 该真实会话在可靠观测期间从未上线到最终投影确认在线，且归属仍有效 | 「前端体验 · CH-3 已上线」；本轮只记一次；工作状态与通信是否就绪可放详情 |
| 暂时失联 | 原在线会话最终投影降为 offline，证据只有 suspected，观测服务本身健康 | 「CH-3 暂时失联，尚未确认停止」；创建可恢复事件，不谎称进程退出或任务失败 |
| 确认离线 | 该会话仍在当前受监测作用域，有未被新生命证据推翻的 stopped 证据 | 「CH-3 已离线」；有进行中任务或未同步回复时提高优先级，指向受影响事项 |
| 恢复连接 | 同一会话先前确有掉线事件，现在出现更新的有效生命证据、最终投影回到在线 | 「CH-3 已恢复连接」；收口原故障，保留断开和恢复时间；不是一次全新上线 |
| 重新建立会话 | 新 session/generation/Composer 的真实接入 | 「CH-3 新会话已上线」；旧事件保留在旧身份，不用新会话消除旧任务或回复同步问题 |
| 正常停止 | 用户停止、结束批次、作用域明确退役或已登记的预期重启 | 「会话已停止」或「批次已结束」；记录每个成员变化，但不用故障红色或逐席位报错 |
| 恢复未完成 | 已知重启或重连操作结束，部分会话仍未得到新接入证据 | 「重启已完成，2 个会话尚未恢复」；不把恢复 Cursor 进程当成全部 Agent 恢复 |
| 停止观测 | 从快照消失、工作区切换或数据源更换，但没有会话停止事实 | 不生成离线通知；显示「已停止监测此工作区」或在原事件说明当前状态未知 |
| 启动时已在线或离线 | 初始快照的存量状态 | 建立基线并恢复既有待处理事项；不一次性弹所有「刚上线／刚离线」 |

首次上线、离线事件、恢复结果都有独立稳定身份。疑似失联到确认离线属于同一 outageEpisode 的升级，不另造两起故障；恢复继续更新该事件，详情保留有意义的状态时间线。之后再次断开才是新的 episode。同一故障不能因 lastSeenAt 或文本改变而反复新增。

真实上线和离线都纳入系统，但不要求每次全局弹出。常规上线、正常结束、未形成明确问题的短暂失联默认就地呈现并安静记录；用户等待的一次批量接入只给汇总，确认的意外离线则按影响程度提升。只有明确处于同一批量创建、预期重启或共同断链原因时作父操作归并；中心能逐个看到成员结果，不能只存一个总数。恢复只在此前已经提示过故障、或用户明确在等恢复时给一次轻提示，否则静默收口原记录。若卡片曾被用户关闭，普通证据刷新不重弹，但疑似状态升级为确认停止且存在未处理工作时可以提升提醒。

### 群体断线和预期操作

- CDP/本地桥断开只证明观察能力受影响；它不是所有 Agent 退出的证据。先发一条「Cursor 过程连接中断」，按最终会话证据继续判定，不额外触发逐席位离线风暴。
- Cursor 主进程确认退出可影响多会话，每个会话记录影响范围，Toast 归并为「Cursor 已退出，8 个会话离线」。单独一个会话异常仍单独提醒。
- 切换账号并重启、开启调试端口重启和自动修复应带通知上下文：operationId、原因、受影响身份、开始和结束、有效期。这不是「未来 120 秒全局静音」：无关会话或不同原因的故障仍提醒。
- 预期重启中的掉线归入原操作详情，恢复后更新同一张；如果重启失败或已达到原业务定义的超时边界，显示恢复未完成。通知不能延长或重试业务操作。
- 睡眠/唤醒和系统时钟调整会破坏直接用墙钟推断的时间差；恢复可靠观测前不生成群体离线事件。精确终止证据可直接入记录，其他情况先重新建立来源基线。当前没有完整的睡眠通知上下文，这是待补的本机观测门禁，不是已实现能力。
- 缺少真实结束时间时保存 observedAt，并写「在此时观察到离线」；不能拿 lastSeenAt 冒充实际退出时刻。事件时间、观察时间、呈现时间分开。
- 排序优先用源 revision / 事件序列和身份，不用到达顺序或所有源混用 updatedAt；旧生命证据不能覆盖新死亡证据，反之亦然。
- 正面停止证据直接通知，不再为了证明而请求一次热态复核、调用模型或另等一个心跳窗口。已有源码的会话判定结果是业务权威，新增门禁只防止错误的通知推断。

## 自动化通知必须覆盖主线和并行支线

一次自动化只建立一个主流程通知，步骤和支线在同一张详情中更新。主阶段、执行结果、取消意图、已发生效果和支线是否结束是不同维度，不使用一枚 done/failed 概括全部。

| 当前阶段或事件 | 通知处理 | 不允许的错误表达 |
| --- | --- | --- |
| 开始本轮自动化 | 关联真实 plan/attempt、冻结该轮服务商和执行模式；可给一次开始提醒，随后原位更新 | 新一轮设置覆盖旧轮的通知内容 |
| countdown | 展示来源倒计时与原有取消入口，当前页可见时不重复弹；剩余秒数不写库、不增加未读 | 每 0.5 秒产生一条消息；通知自己决定何时开始业务 |
| processing | 更新进度，包括来源已有的排队、处理中、重试与待确认语义 | 接收请求或开始重试就报完成 |
| 处理成功且仅处理模式 | 终态明确显示「处理已完成，后续操作未执行」 | 「全部加固并清理完成」 |
| hardening-countdown | 表示处理服务已结束、后续尚未开始；有取消则明确只取消后续步骤 | 取消就声称此前处理也撤回 |
| importing / deleting / cleaning | 更新已经确认的步骤；当前阶段等待时说清在等哪个结果 | 主阶段还在 cleaning 就推测清场已失败；把获取 Token 等局部结果说成全部成功 |
| handover preparing / switching | 更新冻结目标与进度；已发出后是否能取消服从原服务 | 主流程取消就断言已经提交的换号也被取消 |
| handover done / failed | 使用已确认回执记录成功或失败；属于同轮时更新父通知 | 切换请求提交等于 Cursor 已确认；迟来的旧轮回执改写新轮 |
| 主流程 done 且全部必要步骤确认成功 | 「自动化已完成」，一次明确的完成提醒，后台可发送系统通知 | 只看 phase=done、不核对步骤和支线 |
| 主流程 done 但支线未确认 | 「主要步骤已完成，换号结果待确认」等中性或警告结果，支线结果晚到后更新 | 看门狗超时就报换号失败，或先报全成功再悄悄改成失败 |
| 主流程 done 且收尾有警告 | 「自动化完成，清场未完成」等，并区分不影响已成功步骤 | 全部成功；或全部失败、引导重跑已经完成的不可撤销步骤 |
| failed | 指明失败步骤、已完成步骤、未执行步骤和允许的下一动作 | 所有已完成结果都回滚；直接给无条件全链重试 |
| cancelled | 只有服务确认接受并收口才报取消；区分未执行与部分已执行，保留支线真实结果 | 点击取消按钮就提前报已取消；当前阶段不可取消却显示成功取消 |
| 应用退出或崩溃、结果缺失 | 对已记录未结束操作显示「上次流程结果待核对」；仅恢复本地已有证据，不增加远端探测 | 自动改成成功、失败，或主动重新提交操作 |

主流程、清场和换号可能异步完成。通知聚合优先级为：确认失败或需要处理 > 结果未知／待确认 > 带警告完成 > 无警告完成；这只选择呈现方式，不改变业务 phase。通知的成功终态不反向写业务状态，后来出现同轮已确认警告时应追加有效状态，而不是删除此前真实完成步骤。

### 当前结果字段的最小补齐

现有 `AccountAutomationRun` 还不足以无歧义完成上述映射。实施前须以可观察结果字段补齐，不重写编排链、不加等待：

- 稳定的 automationAttemptId / operationId 和更新 revision；planId 继续做关联，runSeq 不再是通知只能猜测的内部身份。
- 该轮开始和结束上下文、执行模式、冻结的来源和目标；必要身份脱敏，不能复制凭据。
- 主步骤和并行支线的结构化结果，例如 not_started / running / succeeded / failed / cancelled / unknown；正常未选步骤为 not_applicable，不记作失败。
- 明确的 warnings、失败步骤、已确认效果与待确认支线；不能靠「收尾异常」等中文字符串正则判断严重性。
- 看门狗结束主等待但支线仍在后台的事实。没有晚到清场结果事件时保持 unknown，不能靠时间过去自动消除警告；换号已有晚到 handover 状态则使用它更新原记录。

保留旧字段给当前 UI 使用，新增展示字段按渐进兼容迁移。旧记录缺证据时显示未知，不凭新设置补造历史。手动服务处理与自动化内部步骤要有关联 ownership：属于父流程时不另弹一张独立处理成功；用户单独执行时才有独立通知。

## 其他不能漏掉的业务事件

下面是核心之外的接入清单，不意味着每项都默认全局弹窗。就地反馈仍是第一选择；后台结束、影响正在运行或需要处理的事件必须进入中心。

| 业务域 | 应覆盖的事件 | 真实结果边界 |
| --- | --- | --- |
| 批量创建 | 提交开始、各项提交和绑定、首次可用、已有会话复用、部分失败、最终结束 | 发起成功不等于上线；返回 failed 可能有部分成功；复用已有待命会话不是新的上线 |
| 批次结束 | 用户结束、运行作用域完成、剩余任务或消息的处理结果 | 正常结束不生成多条异常离线；任务未完成不能被终态标题吞掉 |
| 会话工作 | 新完整回复、明确的本轮结束、生成中断、阻塞、人工问卷／审批、回答成功／失败／失效 | record_reply、原生回复、转录兜底需统一业务身份去重；不能按文本相同误吞不同轮次 |
| 会话队列 | 消息入队、离线等待、真正取走、撤回、解除 hold、随运行退役、回复同步异常 | commandId 只是接受；delivered 不是 replied；已退役消息不能还通知即将送达 |
| 上下文交接 | 文档定位、转录尚未落盘、排队交付、等待新会话、目标取走、失败 | 生成路径和排队不等于读完交接；转录暂不可用不能说完整上下文已保存 |
| 成员身份迁移 | 身份转移成功、任务释放、主控转移、附带上下文交付失败 | 身份成功但上下文失败为部分完成，不回滚或误报整个迁移失败 |
| 组关系 | 建组、入组、出组、解散、主控变更、规划权限变化 | 当前用户操作可就地反馈；他处触发且影响用户时入中心；不通知每次同版本快照 |
| 任务和验收 | 派发、阻塞、待验收、通过、驳回、最终失败、取消、尝试重试、依赖解锁 | 自动重试中间失败不等于最终失败；交接后的处理入口必须重新验证当前权限 |
| 协作和共享记忆 | 发给用户的消息、人工处理需求、可定位的记忆冲突／写入失败、租约或任务异常 | 用户已读不改变 Agent 回执；普通 Agent 状态、每条记忆更新和内部广播不全局刷屏 |
| 独立账号操作 | 导入／登录／绑定、无感切换、切换并重启、失败回退、回退失败、凭据失效、档位识别失败 | warning 和 switched 分开；查询失败不当成 Free 或额度耗尽；邮件等敏感内容不进系统预览 |
| 服务和浏览器 | 卡密验证／失效、已有余额不足结果、处理等待确认、已确认结束、浏览器端口冲突、窗口／workspace 不存在、登录态失效 | 只使用原操作／原查询的结果，不为通知轮询余额、重复提交、自动获取新账户或刷新凭据 |
| Cursor 兼容和维护 | 版本变化、补丁支持或失效、调试连接、自动修复开始／完成／失败／取消、模型目录不可用 | 未支持版本是明确警告，不推测所有功能失效；自动修复引发的断线与原操作关联 |
| 工作区 | 成功识别、切换、未识别、路径失效、数据作用域变更 | 切到新工作区不表示旧会话死亡；页面请求旧范围失败不能影响新范围事件 |
| 用量和上下文 | 可靠数据跨阈值、统计来源持续不可用、重要差异或数据陈旧 | 费用估算不当作官方账单；Token 每次增长不通知；模型／限额变化重新核对阈值域 |
| 导出和清理 | 异步导出完成、附件保存失败、存储扫描和清理最终结果、部分清理失败 | 文件选择器取消是取消，不是保存失败；清理需确认，通知动作不越过原确认 |
| 软件更新 | 新版本、下载完成／失败／取消、安装拦截、升级成功、回滚结果 | 只有原服务确认完成才显示；网络自动探测失败静默；应用重启恢复结果只提示一次 |
| 通知自身 | 持久化失败、原生通知不可用、动作失效、历史查询失败 | 在中心或设置作局部反馈，不向通知系统递归发送其自身故障造成无限通知 |

## 呈现调度和用户偏好

每个事件同时声明：来源类别、严重性、是否需要处理、允许的送达渠道和来源操作。错误不一定是待处理，完成也可能需要用户继续确认，不能只用一个 success/error 来决定所有行为。

- 生命周期和自动化等核心事件默认纳入记录和就地反馈，不等于每次弹出。重要终态、确认意外离线、明确待处理事项遵循上文低打扰规则；声音默认关闭。系统通知是独立的用户开关，还可以按类别关闭。
- 用户可对一个会话设置默认／重点关注／安静；重点关注影响展示优先级，不突破用户关闭的系统通知和声音偏好。不能在第一次看见通知时强弹系统权限。
- 开启安静模式或勿扰后仍保存事件和待处理事实；不因为未弹出而将其标为已读。能否发送系统通知还服从操作系统限制。
- 后台自动化正常完成也是有效系统通知候选，不只发送失败。首次上线、确认掉线和恢复同样可按生命周期类别配置，不能硬编码为永远不提醒。
- 用户正在看确切事项时优先就地反馈；选中会话但滚到旧消息不算正在看新结果。不同来源、不同待处理动作不能为了节省空间合并成没有处理入口的数字。
- 聚合窗口只作用于展示，例如约 1 秒内同源同操作的多成员变化；记录先入可靠内存队列，不让业务等这 1 秒。同一窗口的混合结果展示「6 个上线，2 个未就绪」，而不是只显示成功多数。
- 批量创建和自动化是相关但可并行的事件流。自动化已进入倒计时而其他会话尚在绑定或待命是当前源码允许的真实顺序，通知按实际观察更新父操作和各分支；不能先等全部「上线通知」显示完才发自动化开始，也不能把已经发生的自动化倒排到最后。
- 默认同时只显示一张全局短暂提醒。正在悬停、聚焦或展开详情的卡片保持内容稳定；重要事项先立即进入中心，获得下一展示机会，但不顶掉用户正在点击的按钮。过期普通成功不排成长串「补播」，可以合并或取消展示，重要事实不丢。
- 时效明确的原业务决策不套普通提示的缓慢队列。例如自动化新开始且处于可取消窗口、用户已经离开原页，可更新关联流程提醒而不是另外弹步骤消息；显示的时间来自服务端，取消动作必须核对原 attempt 和当前允许阶段，不能用旧通知取消新轮。若已有原业务闸门或控件可见，就不重复提醒。
- OS 通知送达只表示展示请求成功，不自动标人类已读。点击转到同一条记录；关闭 OS 通知不等于取消业务。
- 不改现有退出语义：关闭到托盘且主进程仍运行时可以后台通知，真正退出或崩溃后不能实时发送。此期间只有已有持久化事实可在下次启动补入历史；不得许诺知道所有漏掉的上下线或擅自安装常驻守护进程。

## 数据和技术结构

采用本地架构：业务事实 → 主进程通知适配器 → 去重和策略 → 通知仓储 → IPC 增量 → 提醒与通知中心。系统通知是同一条记录的另一种送达方式，不另建第二套通知数据。

依赖方向沿用现有 domain / application / infrastructure / renderer。建议最小模块为通知模型、通知服务、SQLite 仓储、IPC、renderer store、ToastHost、NotificationCenter，以及按业务来源划分的薄适配器。不要引入外部通知服务、消息中间件、万能规则引擎或第二套业务状态机。

### 身份和状态

持久化每条通知的稳定 id、来源事件 id、语义去重键、来源实体和作用域、简短内容、严重性、注意级别（活动／需知晓／待处理）、生命周期、创建及有效更新时间、已读时间和已确认阅读的版本、归档时间和版本修订。将「历史事件已结束」与「当前状态仍需处理」分清，不能用已读代表已解决。普通活动不跟踪已读；需知晓和待处理通知才进入未读计数，迟来的阅读确认不能把用户未看到的新结果也标已读。

作用域包括真实的 workspace / run / group / slot / session id 和 generation，不以 CH 编号作身份。应用级更新使用明确的全局作用域。针对同一实体不同操作使用 operation / plan / turn / toolCall 身份，不能只用标题文字或当前时间生成重复记录。

短暂提醒队列、悬停暂停、当前聚焦等展示状态只留 renderer 内存；已读和延后等跨重启状态由主进程持久化。避免把整套 React store 或业务快照重复存到通知库。通知身份同时含父操作归属和 outageEpisode 等事件身份，操作步骤／影响成员保存有限的语义明细，不拷贝所有业务日志。

### 进程和订阅边界

- 主进程统一订阅已有服务。MCP 产生的跨进程事实使用现有 SQLite 协作和任务仓储，不在 MCP 里直接发送 OS 通知或开放人类通知工具。
- 优先消费明确的领域事件或稳定结果。对于只有快照的来源，初始化只建立基线、重建当前待处理状态；不得把全部历史当成新事件。不能可靠识别的完成事件宁可不弹，也不能推测。
- 现有自动化展示结构只有 planId / startedAt，没有统一独立 operationId。接入前为手动操作选择稳定的返回身份或最小 operationId，不改执行顺序、不增加等待。
- 通知专用表属于桌面所有，不新增 MCP 工具。MCP 可能在应用关闭后继续产生业务事实；已有持久化领域事件的来源以独立消费游标补入历史中心，不重放旧 toast / OS 通知。只有内存状态的来源不能声称崩溃后无损恢复；重启只恢复有证据的当前事项，不制造完成事件。源事件保留窗口之外的遗漏也不能凭快照猜测。
- 通知历史使用桌面私有 `notifications.sqlite3` 和自己的版本，不写原业务库，不挪用团队消息表或污染其 schemaVersion。仅把同步 SQLite 放到 worker 仍可能和主线程的业务写锁争用，所以数据库文件也隔离。MCP 的业务事实仍经原共享 SQLite 流转，这个私有库不是另一个 MCP 通信通道。
- 一条记录 upsert 与游标推进用短事务一起提交；通知写入不参与账号或发起链事务，不延长既有执行锁。避免 DB 写入失败后错误地消费掉事件。
- 尤其不能把同步 SQLite 的锁等待塞进主进程业务回调。若沿用同步 `node:sqlite`，通知查询和写入放入专属持久化 worker，忙锁做有界重试、同类记录合并；该 worker 只负责数据库，不执行业务或决定通知语义。
- 通知 IPC 提供自己的 epoch / 单调序列和带 revision 的快照，先稳定订阅再合并初始结果，避免旧 pull 覆盖新 push；中心查询按同一 revision 做分页和计数。已有 DesktopSnapshot 没有全局 revision，conversationRevisions 也只是各通道对话的版本，不能假装所有业务源已经有相同的全序。源内按真实稳定身份和版本比较，跨源由通知服务关联后编号。失联后重新同步记录，不重复发送外部通知。
- renderer 一份独立 store，细粒度订阅提醒和中心；倒计时和 Token 进度不触发整个 App 或过程流重渲染。

### 持久化和降级

第一版中心按页查询，不每次推全量历史；未读和待处理数量由仓储查询，不受当前渲染页数影响。长列表后续按测量结果做窗口化，不影响现有过程流。

建议普通已解决记录保留 30 天；未读、未处理和需诊断的失败记录不静默删除。先提供明确的「清理已读历史」，容量治理按来源统计后决定，不能照数量上限直接截断重要消息。通知不是完整操作审计；需要长期追溯的事实仍引用原业务记录。

写库失败时本轮可用内存反馈并提示「通知历史暂不可保存」，不伪称已持久化；清除或已读提交失败要回滚乐观显示。只记录脱敏摘要和诊断引用，不存 Token、卡密、Cookie、原始请求体、完整账户信息或整段聊天正文。

内存等待队列也必须有界，不能磁盘故障时无限增长。容量不足时优先保留待处理和重要结果、合并可重复状态，普通进度可丢弃；如果未能保存历史事件，明确披露缺口，不能承诺故障情况下仍完整无损。可由原业务事实重建的待处理事项优先恢复，已经丢失的上下线轨迹不补造。

业务结果不等待 OS 展示、动画结束或通知落盘。队列有优先级和聚合窗口，不无限堆积过期成功提示；普通到期项不再弹但历史保留，待处理事项不丢。系统通知至少要可去重，崩溃边界不声称完全 exactly-once：普通项宁可漏一次系统弹窗，中心必须可追溯。

## 动作和一致性规则

1. 通知动作是有限白名单和实体引用，不是持久化回调、任意代码或未验证链接。点击时重新核对当前实体、作用域和权限。
2. 一般动作只定位原功能；重启、安装、账号处理、删除等仍通过已有业务入口和确认，系统通知点击不直接执行高风险操作。
3. 来源不存在时显示「该会话已结束」或「记录已不可用」，允许看原摘要，不误跳到复用同 CH 的新会话。
4. 同一事件的失败到成功或待处理到已解决，更新该条生命周期；有意义的新阶段可重新标为未读，纯遥测变化不能重置已读或重复弹。
5. 问卷在 Cursor 里作答、成员转移或任务取消后，待处理通知同步收口；人类已读不等于业务处理完毕。
6. 同一时刻只保留一个呈现入口。当前页已显示操作失败时，不再额外全局弹同一错误；系统通知仅在后台送出，系统点击后的前台切换不再补弹一次 toast。
7. 重启、升级、重新订阅均不重播旧消息。仍未处理的事项恢复到中心待处理区，不伪装成刚发生。
8. 离线、waiting、stale、用量不变不是已完成证据。任务结果按真实终态、会话回复按真实消息或回合身份判定。
9. Toast 自动收起不标已读，不清除待处理。用户选择「稍后提醒」才设置延后；更新沿用现有服务延后规则，不能被新中心绕过。
10. 声音、系统通知和敏感正文预览分别可控；原生权限不可用时通知中心继续可用。Windows 和 macOS 的原生外观由系统接管，拾光不伪造系统通知。

## 分阶段实施和验收

### 第一阶段核心业务闭环

落实通知模型、持久化、去重、已读、生命周期、中心和统一提醒卡。按小批次完成数据骨架后，首期必须接入：各会话首次上线／失联／确认离线／恢复／正常结束，批量发起的混合结果，自动化开始和各类终态及并行支线，软件更新。补齐必要的源身份和结构化结果，不改业务顺序。缺少这些接入不能宣称首期完成，更不能只把新浮层当作完整通知系统。

该阶段不开 OS 通知，但应用内核心类别偏好、正常操作上下文与故障聚合必须可用；保留原功能页面反馈。

迁移更新提醒时只移交呈现，不复制更新服务。达到原有「查看 / 稍后 / 跳过版本 / 手动检查 / 下载 / 安装门禁」行为等价后，再撤掉旧 toast 宿主；新旧不得同时显示。设置页更新状态仍是业务主界面。

### 第二阶段业务覆盖和待处理闭环

接入问卷、审批、任务验收、回复及队列、上下文与成员交接、独立账号操作、服务和本机维护结果。为上文每个业务域明确已接入事件、就地保留事件、缺少证据的事件；补全过期动作、权限变化和任务重试语义。会话回复只有确认其稳定身份和完成语义后接入，不能等实现时才决定哪些真实重要结果漏掉。

### 第三阶段后台送达和偏好

通过 Electron 主进程接入 macOS / Windows 系统通知，检查应用标识、权限、安装后表现和点击恢复。覆盖用户启用的生命周期、正常流程完成、待处理和失败类别，不只报错。增加系统送达、勿扰和正文预览设置。上下文阈值等次要预警随后接入，不与业务核心一起大改。

每阶段必须具备：

- 同一事件重复推送只产生一条记录；八会话同时结束、失败与成功混合时数量及聚合准确。
- 初始读取晚于实时事件、旧 revision 到达、持久化失败、重新连接和升级后不会回退状态或重放提醒。
- 工作区切换、同 CH 新代次、成员交接、原实体删除时不会串消息、串操作。
- 已读、关闭、延后、归档、业务解决分别验收；中心打开但未阅读不清空未读。
- 当前正在阅读详情、新消息到达、图片或菜单打开时不替换正文，不误关闭父弹层。
- toast 与原页面不双弹；原生与应用内不双弹；原生禁止或不支持不影响中心。
- 长标题、长路径、窄窗、深浅主题、透明背景、200% 缩放、键盘焦点和减少动画不溢出或丢失操作。
- 通知压力下核心倒计时和批量发起耗时不增加；无额外网络探测、全量快照轮询或过程流重渲染。

### 必须用事件序列验证的场景

| 输入事件序列 | 预期结果 |
| --- | --- |
| 启动读取八个已经在线的会话，随后收到相同快照 | 只建立基线，无八条「刚上线」；仍待处理的原事项能恢复 |
| 首帧空快照，后续水合出已有会话；与此同时用户另发起了真实新会话 | 按源就绪和操作身份分别处理，旧会话不伪装新上线，新操作也不被全局启动静音误吞 |
| 一次创建八个会话，六个真正就绪，两个绑定失败 | 一张关联批次通知显示混合结果，明细逐人可定位；六个上线事实不丢，也不额外制造六张同义成功弹条 |
| 全部创建已提交、自动化开始倒计时、部分会话随后才进入待命 | 两条真实事件流并行更新，通知既不阻塞自动化，也不谎称所有会话已可用 |
| 长任务不调用 MCP，但 CDP 仍有新生命证据 | 无离线通知，不用 lastSeenAt 单独判死 |
| 会话变为 suspected，稍后 stopped，之后同代次恢复 | 一个故障 episode 顺次升级和收口，保留变化明细；不会新增三起故障或把恢复说成新会话 |
| 观察器断开但 MCP 会话仍在线 | 一张观察能力异常，不出现全组已离线 |
| 用户切换账号并重启 Cursor，部分会话未恢复 | 一张对应重启操作的结果含每人状态；不报八起意外离线，也不提前报全部恢复 |
| 工作区切换、旧会话从数组消失、同 CH 出现新会话 | 不按消失推断死亡；新身份不会解决旧回复或任务；旧跳转不误开新会话 |
| 主机休眠、唤醒后一次收到所有旧时间戳 | 不制造掉线风暴；建立新观测基线，只处理有独立新事实的事件 |
| 自动化 done，但清场失败、handover 仍 switching | 完成带警告／待确认，不显示全成功；后来该轮换号回执更新原父通知 |
| 仅处理模式 done | 明确后续未执行，未选步骤为不适用，不冒充加固或清场失败 |
| 用户取消第二段倒计时，处理已完成、换号可能已提交 | 显示实际取消范围与已发生步骤；换号状态以回执为准，不说全链撤销 |
| 手动操作重试形成新 attempt，旧结果晚到 | 新旧操作分别归属；旧结果可入原历史，不能覆盖新轮 |
| 交接身份成功，但转录交付失败或 held 尚未取走 | 分别表示身份与上下文结果；待交付不等于已交接完成 |
| 应用退出再启动，上轮只留开始通知没有可靠终态 | 恢复为结果待核对，不自动失败或重跑；关闭期间无历史轨迹的上下线不能编造 |
| 已确认重要事件遇到通知仓储 busy 或损坏 | 业务按原链返回；有界队列和局部降级反馈，不阻塞主线程、不递归刷故障通知 |
| 来源恢复成功但通知更新写入失败 | 原通知不伪称已经持久化收口；内存显示与可恢复状态明确，失败不重跑业务 |
| 用户在导入来源发起登录，切到统计后返回成功或失败 | 结果归原账号和原操作；重要结果可在中心或一张摘要出现，不在统计页顶部挂账号错误 |
| 账号／处理服务切到新对象，旧异步请求才返回 | 旧结果保留原来源；新对象表单、余额和反馈不被改写或清空 |
| 八个设置子页挂载，隐藏维护页检测到无关失败 | 属于局部自动检测，不全局报错；只有确认影响当前运行才升级 |
| 用户当前正在看清理页，清理结束；或离页后才结束 | 前者就地显示真实结果，不双弹；后者重要结果入中心并给一次摘要，显示原操作页入口 |
| 复制路径、改主题、连续调参数、统计更新并在正常会话间切换 | 无全局弹条和未读数字增长，原控件反馈仍清楚；必要生命周期事实安静保留 |
| 用户明确重试同一失败操作，与后台轮询重复报同一失败 | 新 attempt 的用户结果必须可见；同一个故障的重复采样不刷通知，不能用全局冷却把人工重试结果吞掉 |
| 新重要结果在用户阅读旧详情时到达，随后旧版本阅读确认返回 | 保留正在阅读的内容；新结果仍未读，旧确认不误读新 revision；普通候选不形成长串补播 |
| 模态确认打开时普通成功到达，而原业务存在硬闸门 | 成功不遮挡按钮或改变焦点，普通提示可延期／取消；硬闸门仍在原业务立即生效，不等待通知队列 |

上述均为待实现后的验收用例，不是已经运行通过的通知系统测试。现有业务测试只帮助核对源语义，不证明新通知系统已完成。

## 本轮结论和尚缺的实现

此次复核没有进一步修改会话或自动化运行代码，也没有新增接口或发版。规划已从通知外观扩展为真实业务覆盖：每项通知需有身份、触发证据、原因、真实结果、去重／父操作归属、送达策略和可验证的动作。左彩边移除仍是此前独立的小修。

跨页面复核进一步确定：完整覆盖是系统接得住重要结果，不是把所有页面活动塞进弹窗和未读计数。后续实现按页面映射和低打扰决策验收，先保留原 UI 的舒适阅读和交互，再统一历史与重要结果。

真正开工前的必备缺口是：通知仓储与 IPC、最终会话投影的生命周期适配器、可靠的观测上下文、预期重启操作上下文、自动化结构化结果和代次、全局而非页面局部的订阅，以及首期核心事件序列验收。这些属于展示和记录边界，不是另造一套执行链。

实施从最新主线的干净工作树开始，按阶段提交，保护其他开发目录。通知系统未验收完整之前，不为满足外观而删除原来的错误反馈或风险确认。
