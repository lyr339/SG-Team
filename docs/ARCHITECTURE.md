# 拾光 architecture

拾光 (SG Team) is an independent desktop control plane for Cursor multi-Agent teamwork. It does not run inside any Cursor extension and does not depend on any plugin process: channel messages, presence and Agent MCP all flow through the embedded SG Team server plus a shared SQLite database.

Dependency direction:

```text
renderer -> preload API -> Electron main (services)
                              |
                              v
                        SQLite (single database file)
                              ^
                              |
                    stdio Agent MCP (SG Team, per-channel identity)
```

Rules:

- SQLite is the only inter-process medium between the Electron main process and the MCP server processes; both open the same database file and rely on `BEGIN IMMEDIATE` + revision CAS for cross-process atomicity.
- The renderer is a pure snapshot consumer: it receives validated domain snapshots via IPC push/pull and never advances workflow state directly. Task/collaboration writes go exclusively through the Agent MCP tools (`team_task`, `team_message`, …); the desktop IPC surface exposes only read projections plus workflow entry points (team setup, launch, handoff, group membership, account switching).
- Snapshot assembly is layered once, in order: `ChannelMessageRelay` owns conversations/presence for the embedded channels and orders entries by when they entered the dialogue; `LocalSessionBridge` is the transport that merges relay data into the base snapshot; `DesktopSessionService` adds Cursor telemetry and the live process projection on top and seals finished native turns onto persisted replies. The service reacts to transport events once and coalesces pushes into a microtask, so one relay event yields one post-seal snapshot.
- The MCP surface is nine tools in one native `SG Team` entry: the communication contract is exactly two tools, `check_messages` / `record_reply` (`channel_id`, plus an optional per-seat `session` token, see below); the seven team tools are grouped by object (`team_check_in`, `team_tasks`, `team_task`, `team_review`, `team_message`, `team_memory`, `team_run`) with an `action` / `view` enum each (see `docs/TASK-MCP.md`). Cursor-native process events are observed directly and the keepalive marker is `<sg_team_keepalive n="N"/>`.
- Agent identity is `workspace hash + channel + install generation` (`workspaceId:ch-N:generation`); reinstalling a workspace revokes prior generations immediately, so stale MCP processes are fenced.
- Sessions on the same channel are fenced by a per-seat session token, not by waiting for old heartbeats to expire (see "Run modes and the session fence").
- Task, attempt, lease, review and agent-registration state is owned by application/domain services.
- Cursor integration is observation + automation, never a control dependency: CDP (session creation, stream observer, auto-heal) and `state.vscdb` reads degrade gracefully when Cursor is absent.
- Durable storage of raw Cursor/user conversation history remains deferred. Agent-to-Agent collaboration is separate: it is already persisted by `TeamRun + stable AgentSlot + messageId`, with notification, read and response receipts.

## Run modes: the session pool, collaboration groups and the session fence

A workspace has one active run at a time: either a team run (`team-run:<workspace>:<key>`, one-shot, lead + members, started and ended as a whole) or an independent batch (`session-run:<workspace>:<key>`). Both live in the same `team_runs` table; `activeRun` is the newest run of the active workspace. `workspaceRunMode(run) === 'independent'` (`isSessionPoolRun`) is the only pool test in the code base; the `activeRun` semantics were left untouched on purpose (170 call sites).

### The independent batch is a session pool

The independent batch is long-lived: every Cursor session is one seat (`agent_slots`, channel = seat, one `session_token` each) that starts solo and only talks to the user. **Collaboration groups** (`team_groups`, schema v8) are contexts created and dissolved inside the pool at any time: a goal, members, per-member roles, an optional lead, and — through `group_id` snapshots — their own tasks, messages and run-scoped memory. Joining or leaving a group never touches the seat's token, Composer, `generation` or the run status; the pool run stays `running` for its whole life.

- **Membership has one source of truth**: `agent_slots.group_id` (plus `home_role_id` / `group_joined_at`, only set while grouped). `is_solo` flips with it, so every existing "non-solo member" filter (orchestrators, briefings, failover) applies to grouped seats without a second code path. Each grouped seat owns a dedicated group role row (`team_roles.group_id`, `role_key` prefixed with the group's short id, instance numbers continue from the group's max to survive mid-list departures); leaving deletes that row and restores the home role.
- **Lead is decoupled from the role template**: the effective lead of a group is `acting_lead_slot_id ?? lead_slot_id`; authorization overlays `coordination` / `planning` on whoever that is and removes them from a lead-template holder who is not the effective lead. A group may have no lead (decision D2): it then shares goal, messages and memory, and nobody can `plan`.
- **Identity is resolved per tool call**: `refreshIdentity` runs before every team tool, returns `groupId`, and an ungrouped seat gets `not_in_group` (replaces `solo_channel`) with `nextAction: enter_channel_wait`. Join / leave therefore takes effect on the Agent's next call — no MCP restart, no token rotation (locked by `tests/channel-mcp-stdio-groups.integration.test.ts` against the real stdio process).
- **Scoping is a write-time snapshot**: `tasks.group_id`, `team_messages.group_id` / `team_message_threads.group_id` (a thread is fixed to the group of its first message) and `team_memory_items.group_id` are additive, column-existence-guarded columns (desktop and MCP processes migrate independently, in any order). Every Agent-facing view filters by the Agent's current group; operator views read the whole run; project-scope memory is shared across groups; legacy team runs (no group on either side) behave exactly as before. Task keys stay unique per run (a cross-group duplicate key is rejected rather than silently doubled); message groups are inferred recipient → sender when the caller does not pass one, so operator / orchestrator notices to a grouped member land in that group.
- **Orchestration iterates per group** (`groupScopedMembers` / `groupScopedLead`): the dispatcher never assigns across groups, a pool run has no executor for a group-less object, reminders and stale-task alerts go to the task's group lead, run-scoped memory is reviewed inside its group (project-scope by any quality role in the pool), the collaboration sweeper checks each active group's lead heartbeat separately. `TeamFailoverService` still reconciles acknowledgements and recovers an interrupted failover for a pool run, but never completes it, rebinds a seat or fails a lead over — an offline grouped member only sets the group's `attention` flag. `TeamHandoffService` refuses role handoff inside the pool (`handoff_pool_run`): channel = seat, the remedy is remove / add or a session-context handoff.
- **Membership changes are operator actions** (`TeamGroupService`, IPC `team-group:*`, `RunGroupsPanel` on the 运行 page). The repository transaction (validate, mutate, audit row in `team_group_events`, revision bump) is the truth; a rejected transaction has zero side effects. The side effects run afterwards, each fail-soft: a **membership notice** to the affected seat (`channel_outbox.kind = 'membership'`, silent, delivered by `check_messages` with its own suffix — no `messageId`, no `team_message read`, no `record_reply` — because the stage-0 experiment showed the model treating a mid-session identity change under the internal-notification suffix as an injection); lease / review release plus un-targeting of every non-terminal task aimed at the leaving seat (`releaseAgentWork`, otherwise nobody in the group could ever claim it); pending directives to the leaver marked `orphaned: member left` (undelivered ones flip to `not_required`, the sweeper stops chasing them); a `notice` to the group lead; goal changes as a `notice` to every member; dissolution cancels the group's open tasks (`group_dissolved`) and keeps messages and memory read-only. Inside the pool `team_run start` answers `not_applicable`, and `transfer_lead` / `claim_lead` / `clear_acting_lead` act on the group's acting lead.
- **Deferred to later phases** (see `.handoff/DYNAMIC-GROUPS-ROADMAP.md`): adding / removing / re-registering seats without a new batch, per-group usage accounting, restoring group structure from a continuity checkpoint (capsules already record `groups[]`), the roster-as-groups UI, and the tool-surface reshaping.

### The session fence

Channel numbers are global singletons and one MCP process serves every Cursor session, so `channel_id` alone cannot distinguish the old independent session on CH-N from the new team seat on the same channel. The fence makes the arbitration explicit:

- Every `(run, slot)` runtime binding carries a `session_token`, issued at install time and rotated on seat rebuild (`prepareComposerRelaunch`). Team launch does not rotate it (a session created before launch must not be killed by its own team fence). Standby takeover clears it (the standby was already online without a token); manual handoff moves the donor's token with the donor.
- Launch hints, role briefings and delivery suffixes hand the token to the Agent and require it on `check_messages` / `record_reply`. Team tools only take `channel_id`.
- On every communication call the MCP server resolves the channel's owner in the active run (`resolveChannelSessionOwner`, one lightweight query) and evaluates the token *before* any presence write: `ok` (token matches the seat), `legacy` (no token presented: pre-upgrade sessions keep the old contract), or `retired` (`no_run`, `run_completed`, `channel_unbound`, `token_mismatch`). A retired `check_messages` returns a plain-text system instruction that is equivalent to the user asking the Agent to stop; a retired `record_reply` returns `code: session_retired`. If ownership cannot be resolved the fence fails open.
- Switching the conversation scope to a different run (`beginScope`) marks every `channel_presence` row `retired`: old heartbeats no longer represent the new seats. `retired` is an explicit stop phase (offline, `runtimeEvidence = stopped`) that only new life evidence revives: the new session's first tool call (`touchPresence`) or CDP runtime activity for a Composer bound in the *current* run (`touchRuntimeActivity`). Replaying the same scope after a restart does not revive it.

Mode switching therefore no longer hard-blocks on live sessions. `configureWorkspace` and `configureIndependentWorkspace` share `replaceActiveRun` (complete the previous run with a "replaced" reason → write the new bundle → begin the new scope); `endActiveRun` ends the current run explicitly. The only hard block is a team launch whose instructions are still being delivered (or a one-click session creation still running in the desktop). `createNextRun` (a new round of the same team) keeps the "previous run must be over" rule because a team run is a one-shot session, not a mode.

The renderer mirrors the model with a single **运行** page (`src/renderer/src/run/`) instead of separate team / independent tabs: `run-view.ts` folds the snapshot into one view model (mode, phase, seat states, live-seat count, the consequence text of every destructive action), `RunHeader` is the only place a mode is switched, `RunTeamPanel` / `RunIndependentPanel` are the mode-specific areas, `RunSeats` is shared by both modes, and every destructive transition (end, switch mode, new batch, new round) goes through one `ReplaceRunSheet` that asks once only while seats are still live. In the pool the seat list shows every seat (grouped ones labelled "组 · 角色"), and `RunGroupsPanel` under the batch summary carries the group cards (goal, members, lead select, attention), one shared create / add drawer (ungrouped seats with a role template each, optional lead), and remove / dissolve confirmations that reuse `ReplaceRunSheet` with group wording; preview scene `?independent=groups`. Account and Cursor maintenance live behind the top-right account entry (`account` module), not in the main navigation.

## Desktop restart continuity

Quitting or restarting the 拾光 desktop app does not end any Cursor session, by construction:

- The `SG Team` MCP process is spawned and owned by Cursor (its parent is Cursor's MCP utility process), not by the desktop app. It talks to the desktop app only through the shared SQLite file — no IPC, socket or child-process relationship — so the desktop app's lifetime is irrelevant to an Agent's `check_messages` loop.
- Everything the loop depends on is durable: outbox, replies, presence, the reply-sync gate, run/slot bindings and the per-seat session token. Replies recorded while the desktop is down are consumed on the next `pollReplies`; the timeline hydrates from `channel_scope` on start.
- Startup never rewrites `~/.cursor/mcp.json` unless the entry content changed (`reconcileGlobalChannelServers`), so Cursor is not asked to restart the server. `beginScope` (which retires presence and clears gates) only runs on a real run change, never on a same-run replay.
- The CDP hook re-broadcasts the loaded Composers' process snapshots on attach — both when it installs fresh and when a same-version hook survived a force-quit (`'already'` path) — so the live process card is back before Cursor's next model write. A completed CDP response that matches the latest persisted reply by text identity is treated as already archived, so the final answer is not shown twice after a restart.
- The channel service rides out storage blips caused by the desktop's own start/stop (SQLite lock windows): a failing poll iteration is retried on the poll interval until the keepalive deadline; `record_reply` retries `SQLITE_BUSY/LOCKED` in-process. Only a whole keepalive window of failures surfaces, as a structured `storage_unavailable` result with `retryable` (false after `CHANNEL_STORAGE_RETRY_LIMIT` consecutive failures) — never as a raw "database is locked" tool error.
- The server instructions state the contract to the Agent once ("瞬断续接"): a desktop restart is not a stop; transport / storage blips are retried in place; only the session fence, quota / authorization errors or three consecutive failures end the loop.

What does interrupt sessions is orthogonal: restarting Cursor (the Composers and the MCP process die with it — recovery is the session-handoff / recreate flow), and Cursor reloading its MCP configuration (any in-flight long-poll fails once; the Agent re-enters `check_messages` under the rule above).

## Team continuity

- task, collaboration and accepted Agent-managed memory changes are projected into bounded automatic checkpoints;
- unchanged state is content-deduplicated instead of creating timer noise;
- one-click recovery creates a role-specific capsule for each stable AgentSlot and uses the durable message bus for delivery;
- recovery is complete only after every Agent sends a correlated response; channel submission alone is not treated as restored;
- raw chat is never presented as team memory, and users do not manually curate recovery data.

## Task pool persistence

The task pool is durable and uses Electron's bundled `node:sqlite`:

- dedicated database under the 拾光 user-data directory;
- WAL mode, foreign keys and busy timeout enabled;
- normalized `tasks`, `attempts`, `task_events` and `task_pool_meta` tables;
- all aggregate saves use `BEGIN IMMEDIATE` plus revision compare-and-swap;
- lease expiry is swept by the Electron main process, independent of the renderer;
- every installed MCP process is bound to an active SQLite agent registration;
- the production MCP bundle is copied to `Contents/Resources/mcp/index.mjs`, outside `app.asar`, and executed through the packaged Electron binary with `ELECTRON_RUN_AS_NODE=1`.

## Cursor account switching

Switching accounts (FlyCursor-style one-click flow) is orchestrated in the main process: deterministically terminate Cursor (macOS `pkill -x` → poll → `pkill -9` fallback; Windows `taskkill /F`) → logical key backup → write auth keys + account-bound machine identity into `state.vscdb` / `storage.json` / `machineid` exclusively (Cursor must be dead: `node:sqlite` is synchronous and touching the DB while Cursor runs froze the main process) → relaunch with `--remote-debugging-port`. On Windows the relaunch uses the executable path captured from the running process before it was terminated (per-user and all-users Inno Setup installs live in different directories and the latter registers no App Paths entry).

## Platform boundary

Both desktop platforms are first-class. Everything that touches Cursor's own files goes through `src/infrastructure/cursor/cursor-install-paths.ts` (user-data root, install roots, workbench bundle), and process control goes through the platform pair `open/pkill/pgrep/osascript` (macOS) vs `cmd start/taskkill/tasklist/PowerShell Get-Process` (Windows). Two account-automation browser hosts exist: the fingerprint browser (RoxyBrowser, both platforms) and the external system browser (macOS only, AppleScript); Windows always uses the fingerprint host.

## Distribution boundary

`npm run pack:mac` creates an unsigned local macOS app and `npm run pack:win` an NSIS installer plus `win-unpacked` under `release/`. `npm run verify:mac` / `verify:win` launch the MCP bundle through that packaged executable and repeat the real three-process fencing/resume smoke. Signing and notarization are intentionally a later release step and are not implied by the local package.

### Cursor live account switch (2026-09-10)

- A live switch keeps the Cursor process and Composer sessions alive: under one shared hot/cold mutex, 拾光 verifies the installed pump, exchanges the selected vault credential for desktop tokens, serves one nonce-bound payload on the pump's exact loopback endpoint, and accepts success only after Cursor posts a hard readback acknowledgement.
- The acknowledgement is followed by one atomic vault transition (`activateAfterLiveSwitch`): target account becomes active and receives the machine-alignment marker in the same file replacement. A successful cold switch uses `activateAfterColdSwitch` to select the target and clear all markers atomically.
- Compatible `ZMO_SWITCH_V1` pumps installed by another tool are capability-checked and may be reused. They carry no 拾光 owner marker, so the installer does not overwrite or uninstall them. Managed pumps include an owner marker and template revision; marked-but-incomplete runtimes are reported as unsupported.
- Automation starts the live switch after processing and runs it beside the hardening/delete path. Every terminal branch consumes the run-bound result; a failed first attempt retries the same selected successor, never the processed account. Cursor identity hydration receives a 15-second observer grace window.
- A live switch does not change the machine identity. The account row exposes `pendingMachineAlign`; a later cold switch aligns it. Partial success (Cursor switched but local vault commit failed) is reported as a warning, not as total failure.

### Per-account fingerprint window binding (2026-09-10)

- The automation pipeline's fingerprint window is no longer a single global selection: accounts carry a persistent `fingerprintProfileId` binding (recorded automatically at import time — whichever window the token was read from), and the global `bitProfileId` setting degrades to the "default window" for new imports and unbound accounts. `resolveExecutionProfileId` (domain) is the single resolution rule — active account binding ?? default — shared by main-process wiring and the settings-page preview text so the UI can never describe a different window than the one used.
- Window source semantics are split by intent: user-explicit operations (import / open-login-page / manual cleanup) pass their target window explicitly, while mid-run automation calls pass none and reuse the live channel session as the run anchor. This makes a mid-run live handover safe: the active account (and thus resolution) changes, but the deletion chain stays on the window where the run started.
- Ownership guards against wrong-account deletion: the in-browser delete path verifies the page session's account id prefix against the processed account before firing, and the legacy cookie-rotation path refuses to persist/delete with a rotated token whose account prefix differs. Guards engage only for `user::jwt`-shaped tokens and degrade to the legacy behavior otherwise.
- Settings UI: accounts render as a two-column card grid (header identity / meta chips / actions) instead of full-width rows; each card exposes a compact binding chip (window name or 默认窗口) with in-place rebinding; the automation group footer reports the actually-resolved execution window for the current active account. Rebinding does not touch `updatedAt` (handover preference ordering is an account-activity signal, not a UI concern).

### Anti-loop-proof polling: the tick cursor (2026-09-12)

- Incident: a seat agent stopped its `check_messages` long-poll after consecutive keepalives and announced a "polling pause" to the user, breaking the long session. Trigger: the host IDE's anti-loop safeguard injects an authoritative "repeating the same tool calls … ask the user for guidance" reminder, and the long-poll pattern (identical `check_messages` arguments every ~60s) trips it by design. The compacted delivery suffix (single mild "静默续等" clause) no longer outweighed that reminder.
- Cure, mechanism first: every non-error `check_messages` result now names the exact next call, including a fresh `tick` — the persisted per-channel turn counter, monotonic across deliveries, restarts and MCP process respawns. `check_messages` accepts an optional `tick` string the server never validates (fail-open); its only job is to make every poll's arguments unique so identical-call detection never fires. The keepalive body keeps the `<sg_team_keepalive n="N"/>` marker untouched (observer/test contract) and stays a single minimal line — marker + exact next call + a six-character false-positive note — because idle keepalives accumulate in the model context once per minute and their cost must approach zero (the same minimalism constraint that motivated the suffix compaction: no thinking, no prose, straight into the long-poll state).
- Cure, text second: server instructions state the tick contract and name the IDE reminder a false positive; the delivery suffix (user-visible and silent alike) again carries the strong keepalive prohibitions ("直接再调、不输出可见回复、不以任何文字代替调用") that the earlier compaction had dropped; the solo launch hint now explicitly says "不思考、不输出任何文字" before the first `check_messages`.

### Live-response lifecycle guard (2026-09-12, flicker fix)

- Bug: the "Cursor 实时生成中" badge flickered at frame rate while the process stream was presenting. `updateLiveAgentResponse` treated every runtime-inspect frame's `isGenerating` as lifecycle truth; during tool execution the bridge summary reads not-generating (no tokens produced) while observer native frames read generating, so 150ms inspect frames flipped the entry streaming→complete and observer frames flipped it back.
- Fix: the live-response path now follows the exact rule the process view got earlier (`inspectMayEndTurn`) — entries carry a `source` (`native` / `inspect` / `transcript`); while the observer is connected and the entry is observer-owned, inspect frames never end or resurrect it (blocked frames only refresh `updatedAt` as keepalive, since observer frames carry no response text during tool calls); with the observer offline, inspect may end a streaming entry only after 2s of quiet. Ownership upgrades to `native` on authoritative frames and never downgrades on inspect refreshes.
- Verification: typecheck, 156 test files / 1500 tests and knip passed; new guard tests cover the blocked flip, the keepalive refresh, the authoritative completion, the blocked resurrection, and the degraded-mode 2s rule.

### Cursor renderer lag after ~1h: hook scan cost cure (2026-09-12)

- Root cause: the in-page stream hook wrapped the composer data model's write methods and ran a full `processSnapshot` over every bubble of the current turn on every model write (several per second while streaming). Per-bubble derivations (toolInfo JSON walks, thinking concatenation, safePlain clipping, diff parsing) plus a up-to-3MB `JSON.stringify` + CDP binding call per frame made the cost grow O(turn²) — after an hour a turn holds thousands of bubbles and every token write stole Cursor's renderer main thread.
- Cure (hook v30), semantics-preserving:
  - Process payloads are throttled to a 100ms trailing window: frames inside the window carry only the small response/state payload (typewriter granularity untouched), the trailing flush and every terminal (`isGenerating=false`) frame always carry the full process set. The desktop already treats a missing `process` as "no process this frame, keep the previous view", so no desktop change was needed. Escape hatch: `__sgTeamProcessThrottleMs` (0 = every frame full).
  - Per-bubble derivation cache: `toolInfo`/`present`/`safePlain`/`thinkingInfo` results are cached per `bubbleId` with a cheap version fingerprint (lengths / statuses / hydration markers, incl. a deep result fingerprint for late-hydrating MCP results) plus a reference-identity fast path (immutable updates recompute, in-place mutations are caught by the fingerprint). Generating bubbles and terminal frames always recompute fresh, so archived/persisted process blocks never come from cache. Escape hatch: `__sgTeamFactCache === false`.
  - `isUserDelivery` negative caching was deliberately NOT done: a completed tool's result can hydrate in a later frame (2026-09-07 incident), and a wrongly cached negative would permanently hide a real delivery; keepalive results are tiny, so the re-parse cost is negligible.
- Equivalence guard: a test replays a growing turn (thinking streaming, MCP name hydration, result hydration, streaming edit diff, response streaming, terminal frame) through cache-on and cache-off hooks and asserts byte-identical frames; a second test locks the throttle's leading/trailing/terminal frame shapes.
- Verification: typecheck, 156 test files / 1515 tests, knip passed.
- Verification: typecheck passed; channel protocol policy and MCP integration tests updated and extended (tick echo in keepalive with/without session token, tick passthrough, suffix tick hints).

### Post-reply continuation (2026-09-12, handoff process-stream fix)

- Incident: after a session handoff the receiving seat replied "已接手…" via `record_reply` and then kept working on the inherited task inside the same Cursor native turn instead of returning to `check_messages` (09-10: 32 business tool calls, zero polls; 09-11: 243 calls over 1.5 h). The virtual-turn model classified every block after the reply's close boundary as transport gap — dropped by the renderer, skipped by the seal — so the target session showed no live process at all and the work never reached history. Queued user messages could not be delivered either, because the agent never polled.
- Model change: `partitionVirtualProcessBlocks` no longer emits a `gap`; blocks between `reply.createdAt` and the next delivered message form the anchor's **continuation** segment. This is sound because transport noise (check_messages / keepalive thinking / capability) is already filtered per bubble in the hook's `processSnapshot`; what reaches the service after the seal is business work by construction. Legacy replies without `replyToEntryId` keep the time-window fallback and never get a continuation.
- Persistence: `channel_replies.continuation_blocks_json` (idempotent column migration). The seal persists only settled (`done` / `failed`) continuation blocks — appended, immutable once written, clipped by `clipProcessBlockForPersistence` — while running ones stay live until they settle; `process_blocks_json` therefore keeps its byte-stable contract. Persisted ids join `committedProcessBlockIds`, so window replays and restarts do not re-add them to the live view.
- Renderer: `projectVirtualProcessTurns` yields `continuation` (process + response routed by the same close boundary); `projectTurnTimeline` merges `reply.continuationBlocks` with the live tail under the same `turn:<outboundId>` identity; `SessionWorkspace` renders it as a grouped Agent row directly under the reply with the caption "回复后继续工作(中)". Inspector activity / review scope / todo panels and the handoff record read `conversationEntryProcessBlocks(entry)` (reply process + continuation).
- Handoff text: the closing instruction now tells the recipient to return to `check_messages` right after confirming and not to resume the transcript's unfinished task on its own (`HANDOFF_CLOSING_INSTRUCTION`).
- Known limit, unchanged: a `record_reply` issued at the end of a continuation (no newly delivered user message) is still classified as a background reply (`visible = 0`); its text shows live through the continuation response but is not persisted as a timeline entry.
- Verification: typecheck, knip, build and `smoke:channel` passed; event-level tests cover the domain partition, timeline merge, service seal sequence (running → settled → append → window replay byte-stable → next turn isolation → restart hydration), repository/relay persistence, workspace rows and the handoff wording; preview scene `?continuation=1` with `session-continuation-{light,dark}` screenshots.

### Turn liveness vs token streaming: the session-rail activity flicker (2026-09-12)

- Symptom: the "what is it doing" bar under a session-rail card (`.session-row__activity`) blinked on and off while an agent worked, and only ever said `思考中` — never the tool being run.
- Root cause (verified with a read-only CDP probe against live Cursor 3.6.31, not inferred): `ComposerData` has **no** `isGenerating` field; it carries `status: 'generating' | 'aborted' | …` (turn lifecycle) and `generatingBubbleIds` (bubbles currently emitting tokens). The hook derived the frame-level `isGenerating` from `data.isGenerating === true || generatingBubbleIds.length > 0`, which degenerates to the bubble-level set — and that set is **empty during every tool execution** (`tool=run_terminal_command td=loading gCount=0`). So every tool call produced a "terminal" frame: `mergeProcessEvidence` forced running tools to `done`, set `view.generating=false`, archived the turn, and the next thinking token re-opened it. The rail projection is gated on `liveProcess.generating`, so the bar was visible only while a thinking/text bubble streamed — the inverse of what it is for. The same misclassification stamped `completedAt` on executing tools and hid the shell card's live-output state on the session page.
- Fix, one rule per layer:
  - Hook v31 (`cursor-stream-observer.ts`): frame `isGenerating` = turn liveness = `status === 'generating' || isGenerating === true || generatingBubbleCount > 0` (bubble streaming implies liveness; `status` adds the tool-execution stretch the bubble set cannot see; legacy shapes without `status` fall back to the v30 behavior). Bubble-level streaming stays in `process.generatingBubbleCount` and `response.generating`; `parseNativeResponse` now keeps the latter instead of dropping it.
  - Service (`desktop-session-service.ts`): the live answer's `streaming → complete` follows `response.generating` (the frame-level flag stays true while the agent goes on to `record_reply` in a persistent session; using it would leave the finished answer streaming until the 2.5s stale sweep). The live state records `streaming` separately from `generating`; the 150ms runtime fast loop is gated on `streaming`, so long tool runs do not pay a full-turn inspect every 150ms.
  - Rail projection (`session-rail-view.ts`): `sessionRailActivity` is an ordered rule list — offline → none; awaiting user → `等待回答`; turn dead and no streaming answer → none; newest running block → its verb + target; streaming answer → `回复中`; block gap → hold the newest settled block; nothing visible → none. The `处理中` placeholder for "alive but empty view" is gone: it flashed after every reply seal and lied about what was happening. Enter animation is a 120ms fade (no translate). *(Superseded the same day by « Session-rail status line » below: the "none" outcomes and the fade were themselves the remaining blink; the line is now Cursor's persistent subtitle.)*
- Verification: hook VM tests for the three `status` shapes plus `response.generating`; service event sequence thinking → tool(running, 0 streaming bubbles) → gap → thinking → real end asserts `generating` stays true, the tool stays `running`, no archive until the real end, and the rail reads `读取中 · src/main/index.ts` throughout; live-answer completion by bubble flag; rail projection sequences. ### Queued messages leave the timeline: the delivery tray (2026-09-12)

### Cursor lag after ~1h, second root cause: the legacy bridge's trace wrapper (2026-09-12)

- The hook-side cure (v30 throttle + fact cache) left the hook at ~5% of Cursor's renderer main thread; a 15.7s sampling CPU profile of the live workbench (read-only CDP `Profiler`) still showed the main thread 81% busy with ~46% in one chain: `JSON.stringify` **with a replacer** at `workbench.desktop.main.js:59118` (3.7s) and Cursor's own `giantJsonStringify` guard describing the object shape (`eLf`, 3.5s).

Test pins that the wrapped method is never called when the native service exists.
- Still open, recorded here rather than fixed: (a) the app depends on the legacy patch's `__qtComposerBridge` for session creation, `getStatus`, `listComposers` and question submission — owning a minimal CDP-injected bridge would remove the last plugin-era dependency and its 500 ms poller / dead-port `fetch` to `127.0.0.1:36530`; (b) the desktop telemetry `json_extract`s whole `composerData:*` blobs from a 22 GB `state.vscdb` on every changed tick; (c) composer size itself is the multiplier for every remaining per-write cost inside Cursor — bounded only by rotating the seat to a fresh Composer (existing handoff flow) once it grows past a threshold.

### Cursor local storage cleanup: catalog-driven, trash-first, DB pruning in a worker (2026-09-12)

- Why: the machine the lag investigation ran on carried 22.4 GB of `state.vscdb` (1.09 M bubbles / 1,922 composers, `freelist = 0`), 16 GB of checkpoint `snapshots/`, 2.2 GB of `workspaceStorage/` with ≥ 20 orphans and 1.7 GB of stale `state.vscdb.backup/.bak`. None of that is the 1h lag (that is renderer CPU, see the two entries above), but it is 40 GB of disk and makes every write and every telemetry read slower. Settings gained a sixth group, **存储清理** (`SettingsCleanup`).
- Shape: a domain **catalog** (`cursor-storage-cleanup.ts`) describes eight items in user language — what it is, what is lost, risk (`none/low/medium/high`), whether Cursor must be closed, whether it is irreversible or diagnostic-only. Everything downstream (scan entries, default selection, the plan, the confirm copy) derives from the catalog; there is no second list anywhere. `buildCleanupPlan` folds "what the user ticked" into "what can run now": diagnostic items, empty items and unknown ids are blocked with a reason; items that need Cursor closed are blocked while Cursor runs **or while the process state is unknown** (never move files on an uncertain state). The renderer and the main process run the same function — the main process re-scans and rebuilds the plan right before executing, so a stale panel can never delete on old numbers.
- Execution: directory items go through `shell.trashItem` (recoverable; `snapshots/`, `History/`, `logs/` keep the directory and trash its children; cache dirs and orphan workspace dirs are trashed whole); one failing path is recorded in `skipped` and the other items continue. Chat history is the only irreversible item: candidates are indexed composers whose `lastUpdatedAt` is older than the chosen 30/90/180-day threshold, minus every Composer bound to any 拾光 run (`runtime_bindings`, all runs) and minus composers flagged `isBestOfNSubcomposer / isProject / isSpec / isWorktree` (referenced by a parent, by Projects / Specs, or by a worktree on disk — deleting them leaves dangling references). Undated headers are kept. The panel shows protected and skipped counts so the number "298 of 1321" is explainable.
- The database work runs in a `?nodeWorker` thread (`cursor-storage-worker.ts`, one worker per request, first message is the result, then terminate): on a 22 GB WAL database a `bubbleId:` index range count is ~6 s cold and a `length(value)` sum over 800 K bubbles took 190 s — neither may touch the Electron main thread. Size is therefore **estimated**: candidate `composerData` bytes + (sampled mean bubble size × candidate bubble count); the UI labels it 约. Pruning deletes the eight per-composer key families (`composerData`, `bubbleId`, `checkpointId`, `ofsContent`, `messageRequestContext`, `codeBlockDiff`, `codeBlockPartialInlineDiffFates`, `composerVirtualRowHeights`) **one composer per transaction**: a single transaction over a million rows would grow the WAL by the size of the deletion on a disk with 21 GB free and roll everything back on failure; per-composer commits let auto-checkpoint recycle the WAL, a mid-run failure keeps what was deleted, removes only those ids from `composer.composerHeaders` and the per-workspace `composer.composerData` indexes, then throws with progress ("已删除 N / M"). `wal_checkpoint(TRUNCATE)` runs at the end; `VACUUM` only when the user opts in and free disk ≥ 1.1 × file size (otherwise the freed pages are reused by Cursor's later writes and the panel says so). `agentKv:blob:*` (content-addressed) and `inlineDiff:<workspaceHash>:*` are never touched.
- "Is Cursor running" has one outlet now: `cursor-process-probe.ts` (`pgrep -x Cursor` / `tasklist`, exit code 1 = not running, any other failure throws). The account switcher delegates to it (same fail-closed contract, same error text); the cleanup uses the tri-state wrapper (`undefined` blocks anything that needs Cursor closed). The CDP restart keeps its own "any Cursor process still alive" count for quit polling — a different question, deliberately not merged.
- Not done, recorded: the worker chunk ships inside `app.asar`; Electron's worker_threads + asar support has edges, so the first packaged run must verify the worker starts (fallback: `asarUnpack` for `out/main/cursor-storage-worker-*.js`). `legacyPatch()` reads the whole 20 MB bundle to find the marker (a tail read would do). No progress reporting during a multi-minute VACUUM (the port protocol is one message per worker).
- Verification: domain matrix (`cursor-storage-cleanup.test.ts`), analysis + prune on a seeded `state.vscdb` including the partial-failure path via a `RAISE(ABORT)` trigger (`cursor-state-db-analysis.test.ts`), scanner on a temp user-data tree (`cursor-storage-scanner.test.ts`), probe tri-state, worker port timeouts/exit codes, IPC input validation, panel behaviour incl. the `#account:cleanup` deep link (`settings-cleanup.test.tsx`). ### Desktop main-process lag after ~1h: three measured causes, three fixes (2026-09-13)

- Method: read-only reproduction against the production data of this machine (real `state.vscdb`, real `task-pool.sqlite3`, the active run's four seats) with the production code path, plus `ps`/`top` on the running processes. The 拾光 main process (pid alive 16h) averaged **65% CPU** over its lifetime while the Cursor renderer's JS main thread was 5% busy — the desktop, not Cursor, was the bottleneck after the 09-12 hook/patch cures.
- **Cause 1 (dominant), telemetry**: `refreshTelemetry` runs every 250 ms and `readWorkspace` recomputes whenever the `state.vscdb`+WAL fingerprint changes — i.e. every tick while any agent is active. A recompute cost **272–545 ms** (≥100% of a core, back to back); 97% of it was `readTranscriptSignals → transcriptPath`: every workspace composer whose transcript is not under the path-derived project directory (most of them — Cursor 3.6 puts windows in numeric-timestamp directories; this machine has 249 project dirs, 119 numeric) fell through to `transcriptPathGlobalFallback`, one throwing `statSync` per project directory, with no cache. Fix: one `listTranscriptFiles` enumeration (≈5 ms, already run every 2 s for channel activity) builds a `composerId → newest transcript` index; `transcriptPathOf` = workspace-directory `existsSync` (new files visible immediately) else index lookup. `readComposerModelState` (411 KB applicationUser JSON) and the `composer.composerHeaders` parse (0.85 MB, 1037 headers → `parseComposer`) are memoized on the raw JSON text, so an unrelated WAL write no longer re-parses them. Stats that expect misses use `throwIfNoEntry: false`. Measured: recompute **13 ms** (≈5% of a core at 250 ms), cache hit 0.2 ms. Known trade-off: a transcript that first appears in a *non-workspace* directory is found within the index TTL (2 s) instead of immediately; the launcher's composer-binding wait is 45 s.
- **Cause 2, image attachments**: `prepareAttachments` kept the composer's `data:image/…;base64` preview URL (1–2 MB per screenshot, 3.7 MB max per message; 16 MB total on CH-1) in `attachments_json` and in the in-memory entry, and `refreshOutboundDeliveries` did `SELECT *` + `JSON.parse` over every outbound row of the scope every 250 ms (51 ms/tick = 20% of a core for a 2.3 h run with 7 images, linear in images). Fix: thumbnails are `sg-image://local/<path>` URLs (existing protocol, on-demand disk read, CSP already allows it; copy/save already fall back to `path`); pasted images without an extension are stored as `<name>.<ext>` so the protocol allowlist accepts them; the delivery sync reads only `id, delivered_at, retired_at, withdrawn_at` (`listOutboundDeliveryStateSince`). Old rows with `data:` previews keep rendering.
- **Cause 3, renderer structural sharing was dead across IPC**: `shareSnapshotStructure` reused `conversations[channelId]` by `===`, but `webContents.send` structured-clones the snapshot, so the branch never matched: every push (up to ~10 Hz while streaming) replaced every channel array → `visibleEntries` / `projectTurnTimeline` recomputed and every historical `ProcessTurnCard` re-ran `buildProcessTurnView` + `groupProcessSteps`. Fix: the main process stamps `conversationRevisions[channelId]` (same relay array reference ⇒ same number, global monotonic seed) in `getSnapshot()`; the renderer reuses the previous array when the revision matches, falls back to identity when revisions are absent (preview / old main). Live state (`liveProcess`, `liveAgentResponses`, `liveStatusLine`) changes every frame and is untouched; the process stream's hook, sealing and persistence contracts are untouched.
- **Cause 4, every push serialized the whole history**: `emit()` → `webContents.send` structured-cloned the full snapshot (≈8.7 MB for a 2.3 h run) at up to ~10 Hz while streaming, although the timeline only changes on enqueue / delivery / reply. Fix at the IPC boundary only (`register-session-ipc.ts` + `snapshot-push.ts`): a per-webContents ledger remembers which `conversationRevisions` the renderer already holds (from pushes and pull replies; cleared on `did-start-loading`), and each push drops the channel arrays the renderer has — `conversationRevisions` stays complete, `conversations` becomes a delta, `getSnapshot()` pulls stay full, in-process subscribers are untouched. The renderer's `mergeDesktopSnapshot` merges the timeline per channel by revision, independent of arrival order: local revision ≥ incoming keeps the local array, a higher incoming revision with an array replaces it, a higher revision without an array (push/pull race window) is recorded as a gap and `App` pulls one full snapshot for it (`missingConversationChannels`, once per gap); a late (older `updatedAt`) snapshot no longer overwrites sessions or live state but can still fill missing channels and never drops channels. Live state (`liveProcess`, `liveAgentResponses`, `liveStatusLine`) is pushed at full rate as before. `cursorModels` (≈82 KB, changes only with Cursor preferences; reference-stable thanks to the telemetry memo) gets the same treatment through `cursorModelsRevision`, so a live frame carries sessions + live state + revision tables only. Gaps for either section are reported by `snapshotGaps` (`conversation:<ch>@<rev>` / `cursorModels@<rev>`), keyed by revision so one gap triggers exactly one repair pull.

### Seat auto-rotation for the never-ending Cursor turn (2026-09-13)

- **Why**: the persistent-session protocol keeps every seat's Cursor turn in `generating` forever. Measured on 4 solo seats after 20 minutes: pure-keepalive seats had grown to 82–99 bubbles / 0.7–1.1 MB (≈4–5 bubbles per 60 s keepalive: thinking + tool call + result), the active seat 148 bubbles / 1.4 MB, its document 9→18 MB. Cursor persists the whole composer and regroups the current turn on every write, so per-write cost grows linearly with bubble count and `state.vscdb` (22.7 GB) gets slower with it. There is no bug to fix on the Cursor side; the only lever is to swap the Composer before the turn gets big. v1 covers **solo seats only** (`slot.solo`, i.e. independent runs and solo seats inside team runs); team seats involve lead ownership, `team_check_in` state and task leases and are evaluated separately.
- **Safety fix that had to come first — per-round fence re-check**: `check_messages` used to verify the session token only at call start; during the long poll it took from the queue every second (`CHANNEL_POLL_INTERVAL_MS`) without re-checking. Rotating the token of an *online* seat would therefore have let the old session take a user message for up to 60 s, then have its `record_reply` refused — message consumed, reply lost, new session never sees it. `ChannelMessageService.checkMessages` now re-evaluates the fence (`ChannelCheckInput.fence`, wired by the MCP tool when a session token is present) before every queue read from the second round on; a retired session exits with `retired` within one poll interval (≤1 s) and does not refresh presence. Fail-open on fence errors (DB lock etc.), same principle as the tool layer. `prepareComposerRelaunch` was offline-only before, so this window had never been exposed.
- **Fact source — `bubbleCount`**: hook v34 frames carry `fullConversationHeadersOnly.length` (the hook already walks that array; small frames carry it too), the runtime inspect expression reports the same, both land in `CursorComposerRuntimeEvidence.bubbleCount` → `DesktopSessionService.composerBubbleCounts` (newest observation wins, excluded from the evidence fingerprint) → `AgentSession.composerBubbleCount` (rail tooltip "会话体积 N 气泡"). Transcript file size is deliberately not used as a proxy.
- **Decision** (`domain/seat-rotation.ts#seatRotationVerdict`, pure): setting on → run `running` → solo seat → session token issued → composer bound → `composerBubbleCount ≥ threshold` (default **400** ≈ 4 MB; 20–30 min for an active seat, hours for an idle one now that keepalive is 5 min) → not disabled for the channel (2 consecutive failures) → not in cooldown (**10 min** since the last attempt on this channel, success or failure) → **≥2 min** since the last rotation attempt on *any* channel (`SEAT_ROTATION_GLOBAL_SPACING_MS`, so several over-threshold seats after a desktop restart rotate spaced out instead of back-to-back) → idle now (`isSeatIdle`: online, on-duty phase and not processing, queue empty, no pending reply sync, not awaiting the user, live body not streaming — keepalive gaps count as idle so the idle clock is not reset by the model's inter-poll gap) → idle continuously for **5 min** (`SEAT_ROTATION_IDLE_MS`, tracked across snapshots per composer; a new composer restarts the clock) → no user message / reply on the channel's timeline in the last **10 min** (`SEAT_ROTATION_QUIET_MS` via `lastConversationActivityAt`, silent internal notices excluded — this is what separates "the user is chatting on this seat and just paused" from "the seat is parked"; the first cut used 60 s of idleness, which would have rotated the seat the user was actively talking to during a normal reading pause) → presence says `waiting=true` (the server sets it both inside the long poll and on the keepalive return, so this does not strictly mean "inside the call"; either way the rotated token is refused — by the per-round re-check within ≤1 s while polling, or at the start of the next `check_messages` call during the gap) → no manual launch or other rotation in flight. One seat at a time.
- **Procedure** (`application/seat-rotation-service.ts`, subscribed to session snapshots — throttled to one evaluation per second, since each evaluation takes one `TeamControlService.getSnapshot()` and streaming pushes run at ~10 Hz — plus a 5 s fallback tick): (1) read the old session token and resolve the handoff context (`SessionHandoffService.context`: composer + transcript location) *before* touching the binding — `prepareComposerRelaunch` clears `composer_id`, after which `context(channel)` cannot find the transcript; (2) `TeamControlService.prepareComposerRelaunch(channel, { allowIdleOnline: true })` — the new option admits online seats that are waiting with an empty queue, no pending reply and no user question; `undefined` means the seat just stopped being idle → give up silently, reset the idle clock, no failure counted; (3) `deliverFrom(context, self, note, { holdSessionToken: oldToken })` — the hold must be the **old** token (the current one now belongs to the new session; `holdUntilNewSession` would resolve to it and lock the new session out); a delivery failure does not roll the token back (that would resurrect the old session) — the launch proceeds and the outcome message says the context was not delivered; (4) `AgentSessionLauncher.launch([channel], progress, { origin: 'seat-rotation' })` — the existing one-click chain (start prompt with the new binding marker → CDP composer → telemetry-confirmed binding → on-duty), progress pushed on the same `agentLaunchProgress` IPC as manual launches; the plan carries `origin` so the main-process wiring does **not** feed it to `AccountAutomationService.onAllSessionsTriggered` (the post-launch account automation — 奥仔 processing / hardening / account switch — is irreversible and follows only the user's manual batch launch). Result → `DesktopSessionService.noteSeatRotation` → `AgentSession.seatRotation` (`rotating` / `done` / `partial` = new session ready but the handoff message could not be enqueued, so it has no context — amber, persistent / `failed` / `disabled`), rendered as a pill next to the queue badge in the rail (`done` only during the cooldown; the others until replaced or the run changes). Two consecutive failures disable the channel; turning the setting off clears finished notices, turning it back on also clears disabled/cooldown state. Run change clears everything.
- **Settings**: `userData/seat-rotation.json` (`SeatRotationSettingsStore`, default `{ enabled: true, bubbleThreshold: 400 }`, threshold 100–2000 in steps of 50; idle / quiet / cooldown / spacing are constants, not settings); IPC `seat-rotation:get/save-settings`; settings page → 自动化 → "席位自动轮换" (toggle + threshold slider). No confirmation dialog by design: rotation happens while the seat is idle and a dialog would likely be answered after the seat has started working again; the rail pill and the handoff message + "已接手" reply in the timeline are the visible trail.
- **Known residual race**: a user message enqueued in the few milliseconds between the token rotation commit and the old session's fence re-check could still be taken by the old session (its `record_reply` is then refused). The window is the few milliseconds between a round's fence check and its queue read (both inside one poll round); it requires the user to send exactly then — not worth a lock in v1.

### Keepalive window 60 s → 5 min, with the Cursor ceiling measured (2026-09-13)

- **Why**: every `check_messages` keepalive return costs one model turn (thinking + a new tool call + result), i.e. 4–5 bubbles per cycle on a seat that is doing nothing; seat rotation (above) caps the damage, a longer window slows the growth at the source. Delivery latency is unaffected: the queue is polled every second inside the long poll and a message returns immediately.
- **Ceiling, read from Cursor itself** (read-only, `/Applications/Cursor.app/Contents/Resources/app/extensions/cursor-mcp/dist/main.js`, `@modelcontextprotocol/sdk` pinned to 1.25.1 in its `package.json` overrides): the tool-call path is `client.callTool({ name, arguments, _meta: { progressToken } }, CallToolResultSchema, { onprogress, timeout: 36e5 })` — a **1-hour** per-request timeout, `resetTimeoutOnProgress` left at its default `false`, no `maxTotalTimeout`. The workbench side (`MCPService.callTool` / `callToolForLease` → extension host) only threads an abort signal; its `mcp_ipc_timeouts` experiment config covers metadata / lifecycle / dashboard / recovery commands, not tool calls. So the old 60 s was never a client constraint.
- **Change**: `CHANNEL_KEEPALIVE_TIMEOUT_MS` = 300 000 (12× under the ceiling). Override without rebuilding via `env.SG_TEAM_KEEPALIVE_MS` in `mcp.json` (`resolveKeepaliveTimeoutMs`: integer ms, clamped to [10 s, 30 min], anything else falls back to the default); the MCP process logs the effective value on startup (`ready unified (keepalive 300s)`). The desktop's idempotent `mcp.json` registrar (`global-mcp-registrar.ts`) now carries a hand-written `SG_TEAM_KEEPALIVE_MS` over when it rewrites the entry — previously any extra env key was dropped on the next start (and the rewrite itself made Cursor reload the server).
- **Coupled constant**: the telemetry "zombie poll" cap (`CHANNEL_POLL_SILENCE_MS`, channel-level transcript silence while the transport claims waiting/keepalive) is now derived as `CHANNEL_KEEPALIVE_TIMEOUT_MS + 60 s` instead of a hard-coded 60 s. Measured the same day, though, the premise behind that heuristic does not hold for Cursor 3.6 persistent sessions: transcripts are flushed when the turn *ends*, not per tool call — all six healthy waiting seats of the current run had transcripts frozen at their 1 KB opening message for 70 minutes. The verdict therefore fires for every long-lived seat regardless of the cap; it is harmless (`verifyAgentRuntime` only annotates while the MCP heartbeat is fresh, never flips such a seat offline) but effectively dead weight — candidate for removal, not done here. Everything else that looked like a 60 s dependency was checked and is independent of the window: presence staleness (`lastSeenAt` is touched every poll round), the composer-level `check_messages → waiting` verdict (no age limit), the launcher's on-duty wait, the per-round fence re-check, hook noise filtering (by tool name), seat-rotation idle timing (60 s of idleness, not "one cycle").
- Trade-offs accepted: `storage_unavailable` is reported after a full window instead of one minute (the retry streak still stops after 3 windows); Cursor's chat shows the `check_messages` tool running for up to 5 minutes instead of 1 (cosmetic, same as before in kind). Not changed: `CHANNEL_POLL_INTERVAL_MS` (1 s) and `CHANNEL_REPLY_SYNC_STALE_MS` (290 s).
- Verification: `channel-protocol-policy.test.ts` (default value, env override parsing incl. clamps), `cursor-composer-telemetry.test.ts` (zombie cap follows the window: silence of window + 30 s is `unknown`, window + 61 s is `stopped`); existing long-poll suites use injected short windows and are unaffected.

### Windows CDP restart: taskkill exit code, cmd quoting, three-way diagnosis (2026-09-13)

- **Trigger**: the user remembered "9333 had a problem on Windows — it was not picked up, or something". Reading `cursor-cdp-restart.ts` / `cursor-windows-launch.ts` against Windows semantics (nothing here has run on a Windows machine since 09-06) found two defects and one blind spot in exactly that path.
- **taskkill exit code**: the graceful quit is `taskkill /IM Cursor.exe` (no `/F`, on purpose — WM_CLOSE keeps unsaved work). An Electron app has a dozen same-named windowless child processes (renderer, GPU, extension host, pty); for each of them taskkill prints `This process can only be terminated forcefully` and exits non-zero, so `execFile` rejected and the whole restart returned `重启 Cursor 失败：…could not be terminated` — while the main window had received WM_CLOSE and Cursor was in fact quitting. Whatever the user did next (relaunch Cursor by hand, click again) looked like "the port was not carried along". Now taskkill's exit code is ignored; the process-count wait (12 s) is the only verdict, and its stderr is appended to the timeout message when the count never reaches zero.
- **cmd quoting**: the launch was `execFile('cmd.exe', ['/d','/s','/c', 'start "" "<exe>" "<ws>" --remote-debugging-port=N'])`. Without `windowsVerbatimArguments`, libuv wraps the fourth argument in quotes and escapes the embedded quotes as `\"`; cmd does not understand backslash escapes, so `start` received `\"\" \"C:\…\Cursor.exe\" …` and treated `\"\"` as the program. `cursorWindowsStartCommand()` now returns file + args + `{ windowsVerbatimArguments: true }` with the whole start line wrapped in one pair of quotes (cmd's `/s` rule strips exactly those) — the same shape Node itself uses for `shell: true` — and both callers (CDP restart, cold account switch relaunch) pass the options through; the switcher's injectable `execFn` gained the optional third parameter. The 09-06 report "`start "" Cursor.exe` could not find the file" was most likely this defect wearing a different message.
- **Diagnosis instead of "not ready"**: when the port has not answered after 30 s on Windows, `windowsCursorCommandLines()` (PowerShell `Get-CimInstance Win32_Process -Filter "Name='Cursor.exe'"`, UTF-8 prelude) feeds `describeWindowsCdpStartFailure()`: no process → Cursor did not start (message names the executable used); processes without `--remote-debugging-port=N` → a leftover instance took over the launch, quit Cursor fully; processes with the flag but a silent port → reserved range (`netsh … excludedportrange`) or security software, switch ports via `SG_TEAM_CURSOR_CDP_PORT`; PowerShell failure → generic. macOS keeps its previous message.
- **Verification**: `cursor-cdp-restart.test.ts` — the fake `taskkill` now throws with code 128 like the real one (the existing graceful-quit case still succeeds, and asserts verbatim options + the exact quoted command line), new cases for "processes never exit" (timeout text carries taskkill output, no second instance) and the four diagnosis branches; `cursor-windows-launch.test.ts` — command shape, command-line probe parsing/failure, three-way classification. Still to be confirmed on a Windows machine by the user.

### Cache Write is a provider fact, not a Claude-shaped ratio (2026-09-15)

- **Symptom**: the usage popover showed a "Cache Write" bucket for Kimi K3 and for every other model that has no such concept. Root cause, read from the code: every estimated turn is split by a fixed ratio table (`USAGE_PROFILES`, taken from Claude-shaped screenshots — `default` = 0.5 % fresh / 7.4 % write / 92.1 % read), so the estimate manufactures a write share for GPT-5.5 and earlier, Gemini, Composer, GLM, DeepSeek, Qwen and Muse Spark alike; the 09-13 fix (`5a8d8a6`) only special-cased Kimi with a `/^kimi\b/` regex on the price label, and the four-row list rendered "Cache Write 0" even then. Costs were never wrong — those providers' `cacheWritePerM` equals `inputPerM`, so the split changed nothing in dollars — the defect is semantic: presenting a bucket the provider does not have. All five turns in the local ledger were estimates (the persistent Cursor turn never fires `turnEnded`), so the split rule is the whole picture the user sees.
- **Provider check (official pricing pages, 2026-09-15)**: only Anthropic (`cache_creation_input_tokens`, 1.25×) and OpenAI GPT-5.6 / GPT-6 (`cache_write_tokens`, 1.25×) bill a write bucket. OpenAI ≤ 5.5 ("no additional cache-write charge"), Gemini implicit caching (creation at input price; explicit caching has storage rent, not a bucket — Cursor does not use it), Cursor's Grok / Composer ("Cache write —"), Moonshot Kimi (hit / miss only), Z.ai GLM, DeepSeek, Qwen and Meta Muse Spark have two-state input only.
- **Rule**: `hasCacheWriteBucket(price) = cacheWritePerM > inputPerM`. No new field — the table already encodes the fact as the 1.25× premium, and persisted `UsageTurn.price` objects (validated numeric by `cursor-usage-store`) need no migration. `referenceUsage` folds the write share back into fresh input for bucket-less providers (read and total input unchanged, cost identical); `projectUsage` zeroes the fabricated write on **estimated** turns of such providers (`hasFabricatedCacheWrite`) and `upgradeUsageEstimate` now routes through it whenever any such turn exists, so historical Gemini / GPT / Composer ledgers are normalised on the first load and stay idempotent afterwards; exact Cursor settlements are never touched. Presentation: `usageHasCacheWriteBucket(usage)` (any ledger turn's provider has the bucket, or the data carries writes, or — for V2 ledgers without turns — the priced model does) decides whether the popover row / breakdown segment / `cursorUsageDetail` text exist at all; a premium provider at 0 keeps the row (0 is an observation, "no bucket" is not). Unknown models still estimate as the Sonnet tier and therefore keep a write bucket — consistent with the label "· Sonnet 档估算" they already carry.
- **Price table** (snapshot 2026-09-04 → 2026-09-15): added GPT-6 Astra / GPT-6 ($10 / $50 / read $1 / write $12.5 — previously fell into the `gpt` generic at $1.25, 8× under), Composer 1 ($1.25 / $10 / $0.125 — was hitting the `composer` generic), Muse Spark 1.3 ($1.25 / $4.25 / read $0.15 — was Sonnet tier, 2.4× over); DeepSeek collapsed to one `deepseek` entry at V4.1 Flash off-peak ($0.15 / $0.60 / hit $0.003) because DeepSeek bills `v4-pro` requests as Flash from 09-14. Everything else re-checked against Cursor's Models & Pricing page unchanged.
- **Not done, by choice**: the stats page (`SettingsStats`, four-bucket legend, per-model and per-row tooltips) still lists Cache Write — it is an aggregate over sessions and models, and the file is under concurrent edit by another agent this round; the estimate ratios themselves remain screenshot-derived (Anthropic cost is sensitive to the write share: 24 K write tokens were 45 % of a $0.68 Fable turn), a limitation of the method rather than a bug.
- **Verification**: `cursor-usage.test.ts` — provider matrix for `hasCacheWriteBucket`, bucket-less estimates keep read / total / output of the same-ratio GPT-5.6 shape and the same cost, mixed frozen ledger (Kimi + Gemini estimate zeroed, Gemini exact and Claude untouched, source object intact, re-projection idempotent), `upgradeUsageEstimate` on a persisted `default` Gemini turn (normalised once, `toBe` on the second load, Claude passthrough), `usageHasCacheWriteBucket` / `cursorUsageDetail` cases incl. ### Session pool + collaboration groups, phase 1 (2026-09-14 → 09-15)
