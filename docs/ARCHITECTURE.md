# 拾光 architecture

拾光 (SG Team) is an independent desktop control plane for Cursor multi-Agent teamwork. It does not run inside any Cursor extension and does not depend on any plugin process: channel messages, presence and Agent MCP all flow through the embedded SG Team server plus a shared SQLite database.

Dependency direction:

```text
renderer -> preload API -> Electron main (services)
                              |
                              v
                        SQLite (single database file)
                              ^
                              |
                    stdio Agent MCP (SG Team, per-channel identity)
```

Rules:

- SQLite is the only inter-process medium between the Electron main process and the MCP server processes; both open the same database file and rely on `BEGIN IMMEDIATE` + revision CAS for cross-process atomicity.
- The renderer is a pure snapshot consumer: it receives validated domain snapshots via IPC push/pull and never advances workflow state directly. Task/collaboration writes go through the Agent MCP tools (`team_task`, `team_message`, …); the desktop IPC surface exposes read projections plus workflow entry points (session pool creation and end, handoff, group membership, account switching) and exactly one task write, `planTeamGroupTasks` — the user planning tasks into a collaboration group, on the same aggregate path as `team_task plan` (decision D2: planning authority in a lead-less group belongs to the user first).
- Snapshot assembly is layered once, in order: `ChannelMessageRelay` owns conversations/presence for the embedded channels and orders entries by when they entered the dialogue; `LocalSessionBridge` is the transport that merges relay data into the base snapshot; `DesktopSessionService` adds Cursor telemetry and the live process projection on top and seals finished native turns onto persisted replies. The service reacts to transport events once and coalesces pushes into a microtask, so one relay event yields one post-seal snapshot.
- The MCP surface is nine tools in one native `SG Team` entry: the communication contract is exactly two tools, `check_messages` / `record_reply` (`channel_id`, plus an optional per-seat `session` token, see below); the seven team tools are grouped by object (`team_check_in`, `team_tasks`, `team_task`, `team_review`, `team_message`, `team_memory`, `team_run`) with an `action` / `view` enum each (see `docs/TASK-MCP.md`). **Cursor only sees the team tools while the workspace has an active collaboration group** (phase 4 · 4A): one MCP process is one Cursor window and `tools/list` carries no channel, so the seven tools are enabled / disabled together per workspace, re-probed before every `check_messages` return, and announced with one `notifications/tools/list_changed` — no timer, and the fallback for a host that ignores the notification is spelled out in the `joined` membership notice. Tool schemas stay flat objects (no discriminated unions: Anthropic rejects top-level `oneOf` / `anyOf`), locked by `tests/mcp-tool-surface.test.ts` together with a definition-size budget; `npm run measure:mcp` reports the per-turn cost of both workspace states. Cursor-native process events are observed directly and the keepalive marker is `<sg_team_keepalive n="N"/>`.
- **Team messages reach an Agent only through `check_messages`** (phase 4 · 4C). The long poll serves the outbox first (user messages, membership notices) and, when it is empty, the seat's unread team messages inside its current group — bodies inline, receipts marked `notified` + `read` in the same transaction, no reply gate. The MCP process reads the collaboration store directly, so delivery does not depend on the desktop app being open; there is no desktop-side dispatcher, no outbox envelope and no `wake` column. Only member-sent `directive` / `question` messages require `team_message respond`; system dispatches are answered by acting on them. `team_message read` / `inbox` remain as re-read / summary entry points, not as steps of the protocol.
- Agent identity is `workspace hash + channel + install generation` (`workspaceId:ch-N:generation`); reinstalling a workspace revokes prior generations immediately, so stale MCP processes are fenced.
- Sessions on the same channel are fenced by a per-seat session token, not by waiting for old heartbeats to expire (see "Run modes and the session fence").
- Task, attempt, lease, review and agent-registration state is owned by application/domain services.
- Cursor integration is observation + automation, never a control dependency: CDP (session creation, stream observer, auto-heal) and `state.vscdb` reads degrade gracefully when Cursor is absent.
- Durable storage of raw Cursor/user conversation history remains deferred. Agent-to-Agent collaboration is separate: it is already persisted by `TeamRun + stable AgentSlot + messageId`, with notification, read and response receipts.

## Run modes: the session pool, collaboration groups and the session fence

A workspace has one active run at a time, and since phase 2 · 2B-1 the only run it can start is the session pool (`session-run:<workspace>:<key>`). One-shot team runs (`team-run:<workspace>:<key>`, `software-core-v1`, lead + members started and ended as a whole) can no longer be created, configured, launched or given a goal; the ones that exist are archived (`completed`) by the v9 migration and are read-only history — their tasks, messages and memory stay readable, their sessions are retired by the fence. Both kinds still live in the same `team_runs` table; `activeRun` is the newest run of the active workspace (an archived team run that is still the newest run makes the 运行 page show the start page with one explanatory line). `workspaceRunMode(run) === 'independent'` (`isSessionPoolRun`) is the only pool test in the code base; the `activeRun` semantics were left untouched on purpose (170 call sites).

### The independent batch is a session pool

The independent batch is long-lived: every Cursor session is one seat (`agent_slots`, channel = seat, one `session_token` each) that starts solo and only talks to the user. **Collaboration groups** (`team_groups`, schema v8) are contexts created and dissolved inside the pool at any time: a goal, members, per-member roles, an optional lead, and — through `group_id` snapshots — their own tasks, messages and run-scoped memory. Joining or leaving a group never touches the seat's token, Composer, `generation` or the run status; the pool run stays `running` for its whole life.

- **Membership has one source of truth**: `agent_slots.group_id` (plus `home_role_id` / `group_joined_at`, only set while grouped). `is_solo` flips with it, so every existing "non-solo member" filter (orchestrators, briefings, failover) applies to grouped seats without a second code path. Each grouped seat owns a dedicated group role row (`team_roles.group_id`, `role_key` prefixed with the group's short id, instance numbers continue from the group's max to survive mid-list departures); leaving deletes that row and restores the home role.
- **Lead is decoupled from the role template**: the effective lead of a group is `acting_lead_slot_id ?? lead_slot_id`; authorization overlays `coordination` / `planning` on whoever that is and removes them from a lead-template holder who is not the effective lead. A group may have no lead (decision D2): it then shares goal, messages and memory, the user plans its tasks from the desktop, and `team_groups.plan_policy` decides whether the members may plan too — `any_member` (the default for a group created without a lead) overlays the planning capabilities on every member while no lead exists, `lead_only` (the default with a lead, and the backfill for pre-existing rows) keeps Agents out of `plan`. The policy is inert while a lead exists.
- **Identity is resolved per tool call**: `refreshIdentity` runs before every team tool, returns `groupId`, and an ungrouped seat gets `not_in_group` (replaces `solo_channel`) with `nextAction: enter_channel_wait`. Join / leave therefore takes effect on the Agent's next call — no MCP restart, no token rotation (locked by `tests/channel-mcp-stdio-groups.integration.test.ts` against the real stdio process).
- **Scoping is a write-time snapshot**: `tasks.group_id`, `team_messages.group_id` / `team_message_threads.group_id` (a thread is fixed to the group of its first message) and `team_memory_items.group_id` are additive, column-existence-guarded columns (desktop and MCP processes migrate independently, in any order). Every Agent-facing view filters by the Agent's current group; operator views read the whole run; project-scope memory is shared across groups; legacy team runs (no group on either side) behave exactly as before. Task keys stay unique per run (a cross-group duplicate key is rejected rather than silently doubled); message groups are inferred recipient → sender when the caller does not pass one, so operator / orchestrator notices to a grouped member land in that group.
- **Orchestration iterates per group** (`groupScopedMembers` / `groupScopedLead`): the dispatcher never assigns across groups, a pool run has no executor for a group-less object, run-scoped memory is reviewed inside its group (project-scope by any quality role in the pool), the collaboration sweeper checks each active group's lead heartbeat separately. **The desktop orchestrator is the only scheduler** (phase 2 · 2A, decision D1): it dispatches execution and review, chases stale assignees and re-dispatches after a rejection; the lead is told nothing about that machinery. The lead receives exactly three system notices — task `done`, task `failed` after the last attempt (`TaskDispatcher.notifyOutcome`, idempotent per `taskId:status:attemptCount`), and a group member's confirmed Cursor stop (`TeamCollaborationSweeper.sweepMemberAttention`, once per stop cycle, same evidence as `TeamGroupView.attention`) — and the members' automatic `status` reports. The briefings say the same thing from the Agent's side: the lead plans, answers the user and relays real reports; members do not hand-write status messages. `TeamFailoverService` is only the run-close repair (cancel a completed run's open tasks once); an offline grouped member sets the group's `attention` flag and nothing else. The remedy is the operator's: remove / add, or **membership transfer** (phase 2 · 2C, `TeamGroupService.transferMembership`) — the seat's group identity (group role + lead) moves to another independent seat of the pool in one repository transaction, bindings / tokens / Composers untouched, optionally with the session-context handoff document for the new holder.
- **Membership changes are operator actions** (`TeamGroupService`, IPC `team-group:*`, `RunGroupsPanel` on the 运行 page). The repository transaction (validate, mutate, audit row in `team_group_events`, revision bump) is the truth; a rejected transaction has zero side effects. The side effects run afterwards, each fail-soft: a **membership notice** to the affected seat (`channel_outbox.kind = 'membership'`, silent, delivered by `check_messages` with its own suffix — no `messageId`, no `team_message read`, no `record_reply` — because the stage-0 experiment showed the model treating a mid-session identity change under the internal-notification suffix as an injection); lease / review release plus un-targeting of every non-terminal task aimed at the leaving seat (`releaseAgentWork`, otherwise nobody in the group could ever claim it); pending directives to the leaver marked `orphaned: member left` (undelivered ones flip to `not_required`, the sweeper stops chasing them); a `notice` to the group lead; goal changes as a `notice` to every member; dissolution cancels the group's open tasks (`group_dissolved`) and keeps messages and memory read-only. `team_run` is exactly `transfer_lead` / `claim_lead` / `clear_acting_lead`, acting on the group's acting lead; `claim_lead` decides on the lead's presence alone (phase 4 · 4D retired `start` and the `ping` / `pong` / `liveness` probes together with the `channel_liveness` table, and the `renew` no-ops of `team_task` / `team_review`). A grouped seat that is **rebuilt** (`prepareComposerRelaunch`, then a new Composer binds) gets a fresh `joined` notice from `TeamControlService.recordComposerBinding` plus a `member_rejoined_after_rebuild` audit event (actor `system`): the new session started from the solo launch hint and the original notice was consumed by its predecessor.
- **Deferred to later phases** (see `.handoff/DYNAMIC-GROUPS-ROADMAP.md`): adding / removing / re-registering seats without a new batch and the roster-as-groups UI. The tool-surface work landed as phase 4 (4D / 4B / 4C / 4A, see `ARCHITECTURE-LOG.md` « Session pool phase 4 »); merging the nine tools into five (task book D5 = b) was evaluated and not done. Per-group usage accounting landed in phase 2 · 2E (see `ARCHITECTURE-LOG.md` « Session pool phase 2 · 2E: the ledger belongs to the Composer »). Team-level checkpoints / one-click recovery are not deferred but retired (phase 2 · 2D, see "Recovery in the pool model").

### The session fence

Channel numbers are global singletons and one MCP process serves every Cursor session, so `channel_id` alone cannot distinguish the old independent session on CH-N from the new team seat on the same channel. The fence makes the arbitration explicit:

- Every `(run, slot)` runtime binding carries a `session_token`, issued at install time and rotated on seat rebuild (`prepareComposerRelaunch`). Re-installing the same topology (top-up, re-activation) does not rotate it (a session that is still polling must not be killed by its own fence). Nothing else touches it: membership transfer moves group identity between seats, never bindings (standby takeover and the binding-moving manual handoff are gone since 2B-2 / 2C).
- Launch hints, role briefings and delivery suffixes hand the token to the Agent and require it on `check_messages` / `record_reply`. Team tools only take `channel_id`.
- On every communication call the MCP server resolves the channel's owner in the active run (`resolveChannelSessionOwner`, one lightweight query) and evaluates the token *before* any presence write: `ok` (token matches the seat), `legacy` (no token presented: pre-upgrade sessions keep the old contract), or `retired` (`no_run`, `run_completed`, `channel_unbound`, `token_mismatch`). A retired `check_messages` returns a plain-text system instruction that is equivalent to the user asking the Agent to stop; a retired `record_reply` returns `code: session_retired`. If ownership cannot be resolved the fence fails open.
- Switching the conversation scope to a different run (`beginScope`) marks every `channel_presence` row `retired`: old heartbeats no longer represent the new seats. `retired` is an explicit stop phase (offline, `runtimeEvidence = stopped`) that only new life evidence revives: the new session's first tool call (`touchPresence`) or CDP runtime activity for a Composer bound in the *current* run (`touchRuntimeActivity`). Replaying the same scope after a restart does not revive it.

Replacing a run therefore no longer hard-blocks on live sessions. `TeamControlService.createSessionPool` is the one entry point (complete the previous run with a "replaced" reason → write the new all-solo bundle → begin the new scope; the fence retires the old sessions on their next poll); `endActiveRun` ends the current pool explicitly. The only hard block is a one-click session creation still running in the desktop. There is no launch step and no "next round": a pool run is `running` from the moment it is written and `completed` when the user ends or replaces it; `team_check_in` on a `completed` run is refused with `run_completed`.

The renderer mirrors the model with a single **运行** page (`src/renderer/src/run/`): `run-view.ts` folds the snapshot into one pool view model (phase `none` / `active` / `completed`, seat states, live-seat count, groups, the consequence text of every destructive action; an archived legacy team run is projected as "no run" plus `archivedLegacyTeam`), `RunHeader` carries the batch summary and the end action, `RunIndependentPanel` the batch configuration, `RunSeats` the seats, and every destructive transition (end, new batch, remove / dissolve a group) goes through one `ReplaceRunSheet` that asks once only while seats are still live. The seat list shows every seat (grouped ones labelled "组 · 角色"), and `RunGroupsPanel` under the batch summary carries the group cards (goal, members, lead select, attention), one shared create / add drawer (ungrouped seats with a role template each, optional lead), and remove / dissolve confirmations that reuse `ReplaceRunSheet` with group wording; preview scene `?independent=groups`. Account and Cursor maintenance live behind the top-right account entry (`account` module), not in the main navigation.

## Desktop restart continuity

Quitting or restarting the 拾光 desktop app does not end any Cursor session, by construction:

- The `SG Team` MCP process is spawned and owned by Cursor (its parent is Cursor's MCP utility process), not by the desktop app. It talks to the desktop app only through the shared SQLite file — no IPC, socket or child-process relationship — so the desktop app's lifetime is irrelevant to an Agent's `check_messages` loop.
- Everything the loop depends on is durable: outbox, replies, presence, the reply-sync gate, run/slot bindings and the per-seat session token. Replies recorded while the desktop is down are consumed on the next `pollReplies`; the timeline hydrates from `channel_scope` on start.
- Startup never rewrites `~/.cursor/mcp.json` unless the entry content changed (`reconcileGlobalChannelServers`), so Cursor is not asked to restart the server. `beginScope` (which retires presence and clears gates) only runs on a real run change, never on a same-run replay.
- The CDP hook re-broadcasts the loaded Composers' process snapshots on attach — both when it installs fresh and when a same-version hook survived a force-quit (`'already'` path) — so the live process card is back before Cursor's next model write. A completed CDP response that matches the latest persisted reply by text identity is treated as already archived, so the final answer is not shown twice after a restart.
- The channel service rides out storage blips caused by the desktop's own start/stop (SQLite lock windows): a failing poll iteration is retried on the poll interval until the keepalive deadline; `record_reply` retries `SQLITE_BUSY/LOCKED` in-process. Only a whole keepalive window of failures surfaces, as a structured `storage_unavailable` result with `retryable` (false after `CHANNEL_STORAGE_RETRY_LIMIT` consecutive failures) — never as a raw "database is locked" tool error.
- The server instructions state the contract to the Agent once ("瞬断续接"): a desktop restart is not a stop; transport / storage blips are retried in place; only the session fence, quota / authorization errors or three consecutive failures end the loop.

What does interrupt sessions is orthogonal: restarting Cursor (the Composers and the MCP process die with it — recovery is the session-handoff / recreate flow), and Cursor reloading its MCP configuration (any in-flight long-poll fails once; the Agent re-enters `check_messages` under the rule above).

## Recovery in the pool model

There is no team-level checkpoint and no one-click recovery (`TeamContinuityService`, `team_checkpoints` / `team_restore_*`, retired in phase 2 · 2D). The pool never ends by accident — the unit of failure is a single Cursor session — and a seat is recovered by parts that exist anyway, each reading live state instead of a snapshot:

- **seat rebuild** (`prepareComposerRelaunch`, then the new Composer binds; `SeatRotationService` does it automatically for solo seats): same channel, rotated session token, group identity kept;
- **session-context handoff** (`SessionHandoffService`): the context document derived from the previous session's transcript, queued as a plain user message into the target channel — on rebuild, or with a membership transfer (`transferMembershipWithContext`);
- **membership notice on rebind** (2C): a rebuilt grouped seat is told which group it is in and to `team_check_in`;
- **`team_check_in`**: the briefing itself — group goal, tasks, unread messages, shared memory — is always the current state of the run's tables.

Everything a recovery capsule used to carry (goal, group members and lead, tasks, pending messages, shared memory, working files) is therefore either live in the run or carried by the handoff document; group structure history stays auditable in `team_group_events`. Raw chat is still never presented as team memory.

## Task pool persistence

The task pool is durable and uses Electron's bundled `node:sqlite`:

- dedicated database under the 拾光 user-data directory;
- WAL mode, foreign keys and busy timeout enabled;
- normalized `tasks`, `attempts`, `task_events` and `task_pool_meta` tables;
- all aggregate saves use `BEGIN IMMEDIATE` plus revision compare-and-swap;
- lease expiry is swept by the Electron main process, independent of the renderer;
- every installed MCP process is bound to an active SQLite agent registration;
- the production MCP bundle is copied to `Contents/Resources/mcp/index.mjs`, outside `app.asar`, and executed through the packaged Electron binary with `ELECTRON_RUN_AS_NODE=1`.

## Cursor account switching

Switching accounts (FlyCursor-style one-click flow) is orchestrated in the main process: deterministically terminate Cursor (macOS `pkill -x` → poll → `pkill -9` fallback; Windows `taskkill /F`) → logical key backup → write auth keys + account-bound machine identity into `state.vscdb` / `storage.json` / `machineid` exclusively (Cursor must be dead: `node:sqlite` is synchronous and touching the DB while Cursor runs froze the main process) → relaunch with `--remote-debugging-port`. On Windows the relaunch uses the executable path captured from the running process before it was terminated (per-user and all-users Inno Setup installs live in different directories and the latter registers no App Paths entry).

## Platform boundary

Both desktop platforms are first-class. Everything that touches Cursor's own files goes through `src/infrastructure/cursor/cursor-install-paths.ts` (user-data root, install roots, workbench bundle), and process control goes through the platform pair `open/pkill/pgrep/osascript` (macOS) vs `cmd start/taskkill/tasklist/PowerShell Get-Process` (Windows). Two account-automation browser hosts exist: the fingerprint browser (RoxyBrowser, both platforms) and the external system browser (macOS only, AppleScript); Windows always uses the fingerprint host.

## Distribution boundary

`npm run pack:mac` creates an unsigned local macOS app and `npm run pack:win` an NSIS installer plus `win-unpacked` under `release/`. `npm run verify:mac` / `verify:win` launch the MCP bundle through that packaged executable and repeat the real three-process fencing/resume smoke. Signing and notarization are intentionally a later release step and are not implied by the local package.

### Self-update boundary

In-app updating is a **manual component**: the desktop only checks GitHub Releases silently (45 s after start, then every 6 h by default), and a new version is announced by a small bottom-right reminder plus a dot on the settings entry — never a modal, never an automatic download or install. Download and install are user clicks in 设置 › 软件更新. On Windows the install runs the NSIS installer through `electron-updater` (`quitAndInstall(true, true)`: silent, relaunch after); the installer reuses the registry-recorded install directory and mode (a per-machine install prompts UAC once), and it terminates every process under the install directory — including the Cursor-hosted SG Team MCP server (`ShiGuang.exe … index.mjs` is the same executable), so every online seat sees one transport break and re-enters `check_messages` under the 瞬断续接 rule. The install gate therefore blocks while a one-click session creation is running and asks for confirmation while seats are online. On macOS the ad-hoc signed bundle can never pass Squirrel's designated-requirement check, so the mac route is self-owned on the same `AppUpdaterPort`: a static `update-manifest.json` uploaded with every release (sha512 / size / URL per asset), a streamed and hash-verified download, `ditto` staging with `plutil` + `codesign --verify` acceptance, a backup of the old bundle **and** a `VACUUM INTO` database snapshot before the swap, an apply script run through `app.relaunch`, and an explicit-confirm rollback that restores bundle and database together (log entry « App self-update, macOS » 2026-09-16). The Windows update source is `resources/app-update.yml` (written by electron-builder from `build.publish`), the release must carry `latest.yml` + `.blockmap` for Windows and `update-manifest.json` for mac (both uploaded by `release.yml`), and `SG_TEAM_APP_VERSION` in the MCP entry makes the first start after an upgrade rewrite `mcp.json` so Cursor reloads the server with the new code. Neither platform pins a signing identity, so whoever serves the feed can ship code — a custom feed or mirror is a trust decision.

## Desktop notification history

The desktop notification ledger is private to the Electron app in `notifications.sqlite3`. Its worker owns synchronous SQLite reads/writes; it never acquires the shared business database's writer lock. This file is not a second communication medium for Agent MCP processes. Existing domain services remain the authority for workflow outcomes, and notification failure never advances, retries or rolls back those workflows.

The IPC surface accepts only validated history queries, versioned reading, archival, confirmed clearing and preference changes. It does not let the renderer publish events or execute arbitrary saved actions. Reading and closing do not resolve business work; pending actions cannot be archived or cleared. Stored semantic identities and source-local markers prevent startup/replay from resurrecting cleared versions. The renderer store subscribes before its initial pull and does not rewind newer events or preferences.

The quiet center and one-card reminder are integrated with the desktop shell, separately from the conversation render tree. Current sources cover software updates, verified session lifecycles, specific expected restarts, batch launches, structured automation outcomes, independent processing/cleanup/account-switch results, complete replies, native user questions, final task/review states and Agent messages explicitly addressed to the operator. Team review is not human approval; human reading never writes Agent message receipts. Reply association follows stable entry/stream/turn/outbox identities, not text equality. A clipped question is not answered or cancelled; positive runtime evidence can make its original action unavailable without inventing an answer.

Session frames carry exact topology identity; source checkpoints and events commit atomically, with semantic FIFO preserving transitions. A shared projection transport batches at most 100 events per transaction and advances only the checkpoint facts actually included in that transaction. Compact identity checkpoints have a hard 2 MiB bound; conversation text and answer choices are not checkpoint data. Same-array heartbeats use a cached identity signature, not repeated full-history serialization. Unknown write outcomes reload their checkpoint on a subsequent source frame rather than blindly resubmitting. Metadata-only canonical-reference repair respects human clearing; a genuinely new failure may renew attention.

Launch observation follows the original all-submitted trigger; submitted, ready and reused are distinct facts. Automation observes real steps and late child receipts without changing its executor, deadlines or cancellation semantics. Source reading checks the actual body, scroll clipping and foreground dialog; a route change does not acknowledge every result in that page. Collaboration-message navigation validates the exact current run/group/message, pins that body and places it before the graph for this explicit navigation only. Normal group browsing stays graph-first. Other page adapters, extended queue/question sequences, retention/recovery and native delivery remain in progress; see `NOTIFICATIONS-IMPLEMENTATION.md`. Update authority, original switch/cleanup calls and risk gates stay intact; navigation validates session/run/binding/account scope rather than trusting a reused channel or changing active provider/workspace silently.

Real application quit now seals and drains the existing notification producers before closing their ledger. Normal desktop teardown runs once, no final shutdown alerts are emitted, and repeated quit requests join the same drain. Notification waiting has a two-second ceiling; unconfirmed or late transactions are not replayed, and quitting proceeds without claiming they persisted. A tiny private v2 `notifications/runtime.json` marker distinguishes confirmed closing from a previous forced/unfinished exit and preserves possible-history-gap evidence. It contains only timestamps/version/integrity state and opaque runtime/gap identities, not events or credentials, and is not a second event queue. Only repository close acknowledgement can mark the drain confirmed. Last-window/background behavior and updater launch semantics are unchanged; OS-forced termination cannot be guaranteed to drain. Windows native and full installed-application acceptance remain open.

The existing awaiting-user boolean now includes read-only provenance (`runtime` / `process` / `unknown`). A missing, clipped or stale process frame cannot supply confirmed negative runtime evidence; an already observed question action stays unresolved until explicit status, verified unavailability or identity/run cessation. Unknown false does not become a submitted answer or expired action. The annotation uses existing observations, not additional probes.

Queue notifications read a main-only, text/token-free fact cache populated by existing relay enqueue/hydrate/delivery operations. Acceptance returns an optional stable outbox entry identity, not proof of taking or replying. Actual DB run IDs own these events across workspace and binding changes. Queue clipping is not withdrawal. A bounded read-only old-row audit runs only after a committed scope switch/completion to avoid guessing retirement from a cached row an Agent may already have taken; it never joins the original write transaction or fails that business operation. Audit failure is explicitly unconfirmed, not still pending delivery. Explicit handoff IDs may be added to the same existing lightweight periodic query, with a 2,000-ID bound and removal after receipt, so a long-run handoff outside recent timeline rows is still observed. Restart restores only private association identity and starts an uncached DB row as unconfirmed until that original query verifies it; it does not invent deliveredAt from a checkpoint. No new periodic DB/CDP/model polling is added.

Context handoff captures the already-located transcript state, supplemental-record outcome and real outbox identity after the original send. It uses one associated queue record for hold/taking/explicit linked reply, never text matching or command-ID delivery inference. A member migration with attached context adopts that same record; failed context cannot roll back or mislabel the confirmed identity/lead/task-release result. Original results/errors and effect order are preserved under a failed notification observer. Source dialogs acknowledge only their actual displayed event. Navigation to held/pending messages explicitly opens the queue tray; unmounted reveal callbacks cannot fall back into another pane.

Notification delivery is a separate observer of already durable facts. It forwards history immediately but elects one presentation channel per live opportunity: foreground in-app or explicitly enabled background native, not both. Before presentation it rechecks the exact current record, reading, focus and preferences around a private durable claim; unknown claims are not blindly replayed. Delivery claims are not proof of OS display or human reading. Bounded claims/opportunities/native handles keep this out of business execution and global conversation rendering. Filtered-record query counts never replace the global unread summary.

Native notices use Electron only on macOS/Windows, with the packaged Windows application ID. Native/sound/preview/additional life and reply signals default off. Capability availability is read-only and is not permission confirmation; opening settings or toggling the preference sends no test notice. System permission/Focus restrictions remain authoritative. Failed native presentation is disclosed locally with a once-only in-app opportunity where still valid, and new native attempts back off until explicit re-enabling; original records remain. Default OS content is generic; explicit previews defensively remove credentials, email and local paths. Native click/dismiss does not write read or Agent receipts. Click opens an exact center reference, deferring behind an existing modal, never a saved restart/install/answer command. Only the visible exact body can acknowledge reading.

Preferences separate in-app/native category suppression, manual/local-clock scheduled quiet, opt-in extra life/reply dynamics and exact-generation session focus/quiet. Legacy all-channel mutes normalize without accidentally enabling the other channel. Quiet retains records/unread facts and never replays accumulated ordinary successes. A single boundary timer plus the existing resume event handles scheduled quiet, not business polling. Focus affects waiting priority; it never replaces the hovered/focused active card or overrides master/category/quiet gates. Remaining physical OS permission/display/sound and Windows installed acceptance are not proven by adapter mocks or browser previews.

Cross-page operation observers now cover explicit account import/login/window/checkout, browser cleanup, model-policy acknowledgement, patch management, manual debug enabling, question submit/skip and image save.
